# Project navigation (#27)

Tabs are grouped by **project = (profile, source folder)**. `OMP_PROJECT_NAV.projectPath` reads `tab.workspace.projectPath`, falling back to `tab.path` for ordinary checkouts; `tab.path` itself always remains the actual execution folder. The grouped tab bar, sidebar, focus-existing lookup and reorder helpers share this identity. `normalizeWorkspaces` collapses legacy worktree-to-worktree origin chains without changing execution folders or conversation files, and leaves cyclic bindings alone. `normPath` compares separators/trailing slashes and folds case only for Windows drive/UNC paths. Pathless tabs never group. History filter chips still use omp's recorded cwd for saved conversations; they do not guess an origin for closed worktrees whose desktop metadata is unavailable.

- **Tab bar presentation.** A source project with ≥2 conversations is one `TabGroupChip`, labelled by the source folder with its profile chip and member count. The dropdown and expanded sidebar list conversation titles, or “New conversation” while unnamed. A single conversation uses `TabLabel`, also based on its source folder rather than the generated worktree basename. A small `WorktreeIndicator` exposes the source, actual folder, branch and selected base through hover/accessibility details; generated branch/folder names are not primary labels. The project gear opens separate conversation defaults. Closing a group chip still closes one chosen member, never the whole project; middle-click stays a no-op.
- **Member order.** The chip dropdown and the sidebar's expanded rows list members in reverse registry order (`membersNewestFirst`, #38), so a newly opened conversation comes first. Display only: `sessionRegistry` keeps opening order (or the dragged one, below), which `groupTarget`, `open-tabs.json` restore and `closeSession`'s next-active choice read.
- **Reorder (#40).** Drag a project along the tab bar or the sidebar, or a conversation within its project in the chip dropdown or the sidebar; `Ctrl+Shift+PageUp`/`PageDown` (`desktop.tab.moveLeft`/`moveRight`) move the active tab's project one place. `OMP_PROJECT_NAV.moveGroup`/`moveMember`/`shiftGroup` compute the new tab order — every project contiguous, which `groupTabs` renders the same — and `OMP_BRIDGE.reorderTabs(ids)` rebuilds `sessionRegistry` in it, applying only an exact permutation of the open tabs (a stale snapshot is a no-op); `notify` then persists it to `open-tabs.json`, so the order survives a restart. A member drop is in display order, the registry's reverse: a drop above a row is a registry move behind it (`handleReorder` in `app-live.jsx`). Since the registry order is the order, a dragged member to the top of a list is also what a click on the chip and `findProjectTab` pick, and `closeSession` hands focus to the registry's last tab as before.
- **Drag mechanics** (`design/ui/use-drag-reorder.js`, geometry `app/drag-reorder.js`): pointer events, not HTML5 drag and drop — chosen while Tauri's native file drop (`dragDropEnabled`) still swallowed HTML5 drag events on Windows; it is off since the composer's image drop (#50), and pointer events stay for the threshold, Escape and capture. Items carry `data-reorder-list/-id/-axis`; only items of the pressed one's list are targets, so a member never lands among projects. A press becomes a drag after 5 px, so a click still selects; the click a drop produces is swallowed, Escape cancels, and the pointer is captured on the item. Controls inside an item (×, ▾, rename, an inline input) and a `data-no-reorder` region (the chip's dropdown, outside its rows) never start a drag. `.tabs` is outside `.chrome`, so a tab drag never reaches the window-drag handler.

- Recent projects live in `<app config>/recent-projects.json` (`src-tauri/src/recent_projects.rs`), one list keyed per entry by profile, capped at 20 per profile, newest first. Disposable data: an unreadable file reads as empty and the next write replaces it; entries whose folder is gone are hidden, not deleted. Without an app config folder the list lives in memory for the app run (no temp-dir fallback, see `session-model.md`). `recent_projects_touch` canonicalises (`external_open::canonical_folder`), and so does `open_project`'s folder picker — tab paths and recent entries must be in the same form, or a folder picked through a symlink would not match its open tab.
- `live.js` remembers the selected source project only after successful spawn; actual worktree paths remain on the tabs. Recents already represented by an open source-project/profile group are hidden, including old actual-worktree aliases. All recents IPC remains serialized through `_recentsCall` so stale lists cannot overwrite newer touches.
- `openSession`/`+`/`Ctrl+T` request new-conversation setup and spawn only after confirmation; cancellation creates no tab. `openProject` focuses an existing source-project/profile member first, preferring the active member then newest; an explicit actual-folder alias can still focus its matching conversation. Thus reselecting a project with isolated conversations no longer creates a redundant worktree. History resume still matches `sessionFile` and reuses its recorded cwd, bypassing new-workspace preparation. `/new` and profile respawn clear the old conversation identity through `_freshConversationFields`.
