# Reopening tabs on relaunch (#17)

`live.js` keeps `<app config>/open-tabs.json` (`src-tauri/src/open_tabs.rs`, commands `open_tabs_load`/`open_tabs_save`) equal to the open tabs: each tab's folder, profile, conversation `.jsonl` and label, in tab order — `sessionRegistry` order, which a drag or keyboard move rearranges (#40, see `project-navigation.md`) — plus the active index. The shape and the restore arguments are pure helpers in `project-nav.js` (`tabLayout`, `restoreSpec`, regression `test-project-nav.mjs`).

An optional `workspace` field records the selected source project, base ref/commit and isolation flag. It is descriptive: the saved `path` remains the actual working folder and is the only cwd used for restore. The bridge carries the metadata back as `workspaceBinding`, never as a new preparation request. Existing layouts without metadata retain their meaning. A missing worktree is skipped even when its source project still exists; a missing source project does not prevent an existing worktree from reopening.

Before registration, `normalizeWorkspaces` flattens old origin chains (a worktree created from another worktree) to a known source project and normalizes generated default labels while retaining meaningful titles. A metadata-only Git lookup can repair a linked checkout's origin via its common repository directory. If no origin can be recovered, the persisted source identity is retained. Only presentation/grouping metadata changes: saved cwd and session files are never replaced with the source folder, and restore never requests worktree creation.

- **Written continuously, never on quit**: `notify()` → `_persistLayout` compares `tabLayout`'s JSON with the last write and writes on change — one write at a time, latest wins (`_flushLayout`), so the file ends at the newest layout and layouts superseded mid-write are skipped. The updater's installer launch, a relaunch and an OS shutdown end the app without the webview getting a say.
- **Disarmed until the startup restore settled** (`_layoutArmed`): before that the registry lacks the saved tabs, and a write would replace the file with a partial set. When the tabs are exactly what the restore registered, arming *adopts* that layout as already written, so tabs that failed to reopen stay in the file until the first real change — a launch where omp cannot start at all (#34) does not wipe the saved tabs. A tab the user opened, closed or picked during the restore is a real change: `_layoutKey` is left unset and the arming `notify` writes it.
- Startup order: `_refreshProfiles` → `_restoreOpenTabs` → `_setupExternalOpens`. A cold-start "Open with" opens after the restored tabs and ends up active.
- **Settings → Session "Reopen tabs on launch"** (`restoreTabs`, default on; `docs/architecture/settings.md`), read from the stored tweaks at `live.js` load (`OMP_TWEAKS_STORE`), so the boot restore sees it before React mounts. Off: `_restoreOpenTabs` opens nothing and never calls `open_tabs_load`; the file is left untouched, since arming adopts the empty layout as already written, and is first rewritten at the first real tab change.
- `_restoreOpenTabs` spawns tabs one at a time via `_startProjectSession(…, {activate: false, remember: false})` — no activation round-trips per tab, no reordering of recent projects. Activation is decided *after* each spawn (several IPC round-trips) against the then-active tab: the first restored tab is activated as soon as it has spawned, the saved active one takes over when it spawns, and a tab the user opened or picked meanwhile keeps the focus. A failed activation is logged and the loop goes on.
- `open_tabs_load` filters against the file system: a gone folder drops the tab (reported in a note), a gone conversation file (an empty conversation omp never wrote) reopens as a fresh tab on the folder, a pathless tab without a conversation is dropped. The resume path is still validated by `start_session` against the tab's profile.
- **No config folder, no file**: when the app config folder can't be resolved, the layout is kept in memory (`OpenTabsStore`'s `config_file::ConfigFile` holds the bytes the file would, so a webview reload still restores through the same `restorable` filter) and the next launch starts with no tabs. There is deliberately no temp-dir fallback: a planted `open-tabs.json` there would choose the folders, profiles and conversations omp starts in.
- Tab ids are `session-<ms>` from a monotonic counter (`_lastSessionMs`): back-to-back restores can start within one millisecond.
- **Unanswered questions** are recovered from the resumed process's raw entries and active leaf, not from its filtered `get_messages` history or the old process's volatile request ids. A restored ask remains answerable; its answer continues the conversation as a new user reply without replaying tools. See `ask-dialog.md` for eligibility, cancellation persistence and limits.
