# Interface language (`app/i18n.js`)

The window's own controls can be translated at runtime. omp's text — replies,
tool output, ask questions, plan contents, model names, slash-command
descriptions — comes from the agent and is never translated here; so are
runtime values from Rust (versions, saved paths, profile names) until the row
that shows one calls `OMP_TR` itself.

## Contract

- **The English source string is the key.** `OMP_TR("Close tab")` returns the
  current locale's translation, or `"Close tab"` itself when the dictionary has
  no entry. Nothing is extracted, no key catalogue is maintained, and an
  untranslated string is never missing from the UI — it just stays English.
- A locale file registers its strings with
  `OMP_I18N.add("<code>", { "<English source>": "<translation>" })`
  (`src/app/i18n-zh.js`). Registering a code adds it to `OMP_I18N.available`.
- **Call at render/call time; never cache the result.** `OMP_TR` follows
  `OMP_I18N.set()`, which app-live.jsx applies before the tree renders.
- `{name}` placeholders are filled from the optional vars object; an unknown
  placeholder is left as written, so a translation can keep `{n}` wherever the
  language wants it.
- Plurals: `OMP_I18N.plural(n, one, other, vars)` uses `one` for `|n| === 1`
  and `other` otherwise, and also exposes `n` as `{n}`. A dictionary entry for
  the `other` source string may instead be an object of `Intl.PluralRules`
  categories (`{ one, other, few, many, … }`) — used for languages with more
  than two forms.

## Load order (`src/index.html`)

`app/i18n.js` and each dictionary load right after `app/marked-setup.js` and
before every other app module. They must precede:

- `app/settings-schema.js`, whose `search()` indexes both the English source
  and the translated label/description;
- every Babel file that calls `OMP_TR` — the lookup happens at render time, so
  only the global must exist.

`app/i18n.js` reads the stored `locale` tweak straight from the
`omp-desktop:tweaks` localStorage entry, so the first paint is already in the
chosen language. `app/i18n-zh.js` loading afterwards re-resolves that request
once the dictionary exists; both happen before React mounts, so there is no
flash of English.

## Switching

`locale` is a normal tweak (`app/constants.js` `TWEAK_DEFAULTS`, Settings →
Appearance → Language, options `auto` / `en` / `zh`):

- `auto` follows the OS language (`navigator.languages[0]`, matched by full tag
  then by primary subtag, so `zh-CN` picks a `zh` dictionary);
- `app-live.jsx` calls `OMP_I18N.set(t.locale)` during render when the tweak
  value changed — before children render, so one pass repaints in the new
  language. `set()` is idempotent and sets `document.documentElement.lang`;
- `i18nchange` is dispatched on a real change for code outside React.

## Adding or translating a surface

1. Wrap the string at render time:
   - JSX: `{OMP_TR("Close tab")}`, props: `title={OMP_TR("Close tab")}`;
   - plain `app/*.js` IIFE: `window.OMP_I18N.t(...)` inside the function body
     (a top-level destructure would add a load-order constraint).
   - A composed string (schema text + a runtime suffix) translates the schema
     part first: `desc={`${window.OMP_I18N.t(row.desc)}${scope}`}`
     (`settings/rows-agent.jsx`).
2. Add the English source string as a key to `src/app/i18n-zh.js`. Nothing
   else: no keys file, no component change.
3. `node tests/test-i18n.mjs` fails if a Settings section/group/row label or
   description has no entry, and if any `OMP_TR("…")` literal in
   `src/design/*.jsx` has none (a small allowlist covers paths, units, product
   and tool names, and the example address), so the chrome cannot silently
   fall back halfway.

The desktop chrome is translated at its render chokepoints: the shared
`design/settings/controls.jsx` (`SettingsRow` label/desc, segment labels,
slider units, aria/title text) and `design/settings/page.jsx` (chrome,
section/group headings, search results) for every Settings row; each other
surface wraps its own static text and `title`/`aria-label`/`placeholder`
values at render (`design/chrome.jsx`, `project-sidebar.jsx`, `composer.jsx`,
`chat/*`, `subagents/*`, `git/*`, `panels.jsx`, the browser and terminal
panels). The keymap action labels come through `SettingsRow` in
`settings/shortcuts-editor.jsx`; the slash palette and command bridge wrap
`c.hint`/`c.group` in `composer.jsx`.

## Limits

- Editing an English string that a dictionary uses as a key silently drops that
  translation (the source string no longer matches). Treat a wrapped English
  string as a stable API, or add the new spelling to the dictionary.
- Highlighting a search query only marks text that still contains the query:
  searching English while a translated UI is active finds the row (both
  languages are indexed) but does not mark the translated words.
- Layout is not adapted to longer translations yet; the Settings page uses
  flexible rows, other surfaces may clip.
- `document.title` and the app's product name stay English.
- A locale file is a plain `<script>`; `scripts/build-frontend.mjs` copies it
  into `dist/` with the rest of `src/`, so no build change is needed.

## Testing

`tests/test-i18n.mjs` loads the real `app/i18n.js`, `app/i18n-zh.js` and
`app/settings-schema.js` against a `window` stub, then checks: fallback and
interpolation, tag matching (`zh-CN`/`ZH_tw` → `zh`), `auto` following the OS
language, plural forms, idempotent `set`, the stored-locale/dictionary-arrival
order, full Settings label/description coverage, translated search, and the
`locale` row.
