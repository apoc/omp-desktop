# Interface language (`app/i18n.js`)

The window's own controls can be translated at runtime. omp's text — replies,
tool output, ask questions, plan contents, model names, slash-command
descriptions, a provider's error message — comes from the agent and is never
passed to `OMP_TR`; runtime values from Rust (versions, saved paths, profile
names) stay as they are too. A value that is either a desktop fallback or
runtime text (a live-voice or updater error) may go through `OMP_TR`: only an
exact key match translates, so the desktop's own fallback is translated and
Rust's text passes through.

## Contract

- **The English source string is the key.** `OMP_TR("Close tab")` returns the
  current locale's translation, or `"Close tab"` itself when the dictionary has
  no entry. Nothing is extracted, no key catalogue is maintained, and an
  untranslated string is never missing from the UI — it just stays English.
- A locale file registers its strings with
  `OMP_I18N.add("<code>", { "<English source>": "<translation>" })`
  (`src/app/i18n-zh.js`).
- **Keys are context-free.** One English source string has one translation
  everywhere, so a word used with two meanings needs two source strings (the
  git browser's "stage" is the `git add` action, the layout's centre column is
  "½ stage").
- **Call at render/call time; never cache the result.** `OMP_TR` follows
  `OMP_I18N.set()`. Call `OMP_TR` itself (or `window.OMP_I18N.t` in a plain
  `app/*.js` file) — no per-file alias, so the coverage test sees every call.
- A `React.memo` component whose props do not change still has to repaint when
  the language does: call `OMP_I18N.useLocale()` at the top of a memoized
  component that renders `OMP_TR` text (chat bubbles, tree rows, `BranchMenu`,
  `ProfileMenu`, `SettingsPage`, …). Plain components repaint with `App`,
  which subscribes too.
- `{name}` placeholders are filled from the optional vars object; an unknown
  placeholder is left as written, so a translation can keep `{n}` wherever the
  language wants it.
- Plurals: `OMP_I18N.plural(n, one, other, vars)` uses `one` for `|n| === 1`
  and `other` otherwise, and also exposes `n` as `{n}`. Only the `other` source
  string is a dictionary key: its entry is either one string for every count
  or an object of `Intl.PluralRules` categories (`{ one, other, few, many, … }`)
  for languages with more than two forms.
- A sentence with a runtime value in it is one key with a placeholder
  (`"also bound to “{name}” — that binding wins"`), never fragments around the
  value: another language orders the sentence differently.

## Load order (`src/index.html`)

`app/i18n.js` and each dictionary load right after `app/marked-setup.js` and
before every other app module. They must precede:

- `app/settings-schema.js`, whose `search()` indexes both the English source
  and the translated label/description;
- every Babel file that calls `OMP_TR` — the lookup happens at render time, so
  only the global must exist.

`app/i18n.js` reads the stored `locale` tweak straight from the
`omp-desktop:tweaks` localStorage entry (`tweaks/use-tweaks.js` `STORAGE_KEY`;
rename both together), so the first paint is already in the chosen language.
`app/i18n-zh.js` loading afterwards re-resolves that request
once the dictionary exists; both happen before React mounts, so there is no
flash of English.

## Switching

`locale` is a normal tweak (`app/constants.js` `TWEAK_DEFAULTS`, Settings →
Appearance → Language, options `auto` / `en` / `zh`):

- `auto` follows the OS language (`navigator.languages[0]`, matched by full tag
  then by primary subtag, so `zh-CN` picks a `zh` dictionary);
- `app-live.jsx` subscribes with `OMP_I18N.useLocale()` and calls
  `OMP_I18N.set(t.locale)` in a layout effect when the tweak changes: the
  subscription re-renders `App` (and every memoized subscriber) before the
  browser paints, so a switch never shows a frame of the old language.
  Setting the locale during render would update subscribed components while
  `App` renders, which React reports as an error. `set()` is idempotent and
  sets `document.documentElement.lang`;
- the webview's `languagechange` event re-resolves `auto` (an explicit choice
  stays), and the same subscription repaints the tree.

## Adding or translating a surface

1. Wrap the string at render time:
   - JSX: `{OMP_TR("Close tab")}`, props: `title={OMP_TR("Close tab")}`;
   - plain `app/*.js` IIFE: `window.OMP_I18N.t(...)` inside the function body
     (a top-level destructure would add a load-order constraint).
   - A composed string (schema text + a runtime suffix) translates the schema
     part first: `desc={`${window.OMP_I18N.t(row.desc)}${scope}`}`
     (`settings/rows-agent.jsx`).
2. Add the English source string as a key to `src/app/i18n-zh.js`. Nothing
   else: no keys file, no component change.
3. `node tests/test-i18n.mjs` fails if a Settings section/group/row label or
   description has no entry, if a desktop string table entry (keymap action
   labels and groups, the desktop slash commands' hints and groups, approval
   modes, thinking-level hints) has none, and if any literal passed to
   `OMP_TR`, `OMP_I18N.t` or as `OMP_I18N.plural`'s `other` form — including
   both branches of a `cond ? "a" : "b"` argument — anywhere in `src/design/`,
   `src/app/` or `app-live.jsx` has none. Units, paths and product names are
   not wrapped at all. A table private to one component (`_PC_WORD`, or
   the file preview's `FILE_STATES`, shared with the files panel) is not
   enumerated: give its entries keys when you add them.

The desktop chrome is translated at its render chokepoints: the shared
`design/settings/controls.jsx` (`SettingsRow` label/desc, segment labels,
slider units, aria/title text) and `design/settings/page.jsx` (chrome,
section/group headings, search results) for every Settings row; each other
surface wraps its own static text and `title`/`aria-label`/`placeholder`
values at render (`design/chrome.jsx`, `project-sidebar.jsx`, `composer.jsx`,
`chat/*`, `subagents/*`, `git/*`, `panels.jsx`, the browser and terminal
panels). The keymap action labels come through `SettingsRow` in
`settings/shortcuts-editor.jsx`; the slash palette and command bridge wrap
`c.group`, and `c.hint` of desktop commands only (omp's hints are omp's text).

## Limits

- Editing an English string that a dictionary uses as a key silently drops that
  translation (the source string no longer matches). Treat a wrapped English
  string as a stable API, or add the new spelling to the dictionary.
- Highlighting a search query only marks text that still contains the query:
  searching English while a translated UI is active finds the row (both
  languages are indexed) but does not mark the translated words.
- Layout is not adapted to longer translations yet; the Settings page uses
  flexible rows, other surfaces may clip.
- `document.title` and the app's product name stay English.
- `auto` matches by primary subtag, so `zh-TW`/`zh-HK` get the Simplified
  Chinese dictionary until a `zh-Hant` one is registered.
- A transcript note the desktop writes (a refused steer/follow-up) keeps the
  language it was written in.
- A locale file is a plain `<script>`; `scripts/build-frontend.mjs` copies it
  into `dist/` with the rest of `src/`, so no build change is needed.

## Testing

`tests/test-i18n.mjs` loads the real `app/i18n.js`, `app/i18n-zh.js`,
`app/settings-schema.js` and the modules owning the desktop's string tables
against a `window` stub, then checks: fallback and interpolation, tag matching
(`zh-CN`/`ZH_tw` → `zh`), `auto` following the OS language and
`languagechange`, plural forms, idempotent `set`, the stored-locale/dictionary
arrival order, full Settings label/description coverage, the string tables,
every translated literal (a file that does not parse fails the check),
translated search, and the `locale` row.
