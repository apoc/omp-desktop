# Goal mode

omp's goal mode over RPC (omp ≥ 18.4.11, the current floor): the `goal` command (`get | create | resume | pause | drop`, `objective`, `token_budget`), the `goal_updated` frame (`{goal, state?}`) and `get_state.goal` (`GoalModeState | null`). `src/app/goal.js` (`window.OMP_GOAL`, regression `test-goal.mjs`) is the pure reducer — a tab's `{known, goal}`, the transcript rows, the strip's view; `live.js` keeps its result in `state.goal`, snapshotted per tab like the transcript; `design/goal-strip.jsx` renders it above the composer and `design/chat/goal-row.jsx` in the transcript; `app/use-goal-mode.jsx` owns the composer's goal mode (a per-tab `{mode, budget, error}` kept in React, like plan mode, since omp never sees it; the plan/goal exclusion is `OMP_GOAL.composerGate`) and the auto-continue setting, read per profile rather than per tab.

- **Rows only for news.** `fromFrame` returns a row only when the tab already knew its goal state (`known`, set by the first `get_state` or frame after a reset). A fresh or respawned process re-reports its goal — and pauses one it finds active at startup — before the desktop's first `get_state`; those frames stay silent. Snapshots never produce rows. Rows are live-only (kept in place by the get_messages merge, gone after a restart).
- **Completion** sends one `goal_updated` (`status: complete`, `mode: exiting`); at the end of that turn omp clears the goal without another frame and `get_state.goal` turns `null`. The reducer keeps a completed record across null snapshots until it is dismissed, another goal appears or the transcript resets. Until that turn ends omp still reports the completed goal, so `dismiss` remembers its id (`dismissedId`) and later snapshots or frames of it are ignored.
- **Abort pauses.** omp's `abort` pauses an active goal, and only `goal resume` restarts it. `abort()` sets `userAbortInFlight` until its id-less response, so that pause is labelled as the user's stop. The flag is per tab (snapshotted like the transcript): a pause frame and response held back by a tab switch are replayed on the way back, and a `dropped` replay clears it. A resumed goal already over budget flips to budget-limited at the abort's accounting and is not paused.
- **Start.** `OMP_BRIDGE.goalStart` sends `goal create`, then `get_state`, both with the default timeout so a reply held back by a tab switch resumes the sequence on the way back. When omp did not start a goal turn itself (`ompStartedTurn`: streaming, or unsettled with neither a background job pending nor messages queued — a job's wake-up does not carry the goal, and omp skips a continuation while follow-ups wait), the objective goes out as the first prompt, as omp's own `/goal` does. If omp is unsettled anyway, it waits in the queue strip instead of as an early bubble (`_sendQueued`), so it never shows twice — but still as a `prompt` (`streamingBehavior: "steer"`), never a `steer`: only omp's prompt path adds the goal-mode context (objective, budget, when to call it complete) to the turn, and an idle steer is drained without it. Mid-turn it is steered. Enter and the follow-up chord both start the goal. omp's `/goal` is TUI-only: over RPC it is not in `get_available_commands` and reaches the model as plain text, hence the desktop's local `/goal` entry; `/goal <objective>` turns goal mode on with the objective back in the composer. Once the tab has an open goal, its goal-mode draft is dropped.
- **Auto-continue** is omp's `goal.continuationModes` setting (default `["interactive"]`): over RPC omp continues a goal between turns only when it holds `"rpc"`, starting each such turn with a hidden `goal-continuation` custom message (`live.js` puts a `continue` row above it). No RPC sets it: `src-tauri/src/goal_config.rs` runs `omp [--profile=<id>] config get|set goal.continuationModes` (through `omp_cli::run`, shared with `stats.rs`) (commands `goal_continuation_get` / `_set`) and edits only the `"rpc"` entry. The profile must go through `resolve_owned` first — `omp --profile <unknown>` silently creates that profile's directory. Running tabs of the profile pick the change up live (omp's settings watcher). It writes the profile's global config; a project config that sets the key wins.
- **Plan mode and a goal exclude each other**, as in omp (it refuses `create`/`resume` in its plan mode; its TUI blocks plan mode while a goal exists): the plan pill, `/plan` and `app.plan.toggle` are off while the composer is in goal mode or the tab's goal is active, paused or budget-limited; the goal pill while plan mode is on or the tab already has such a goal.
- omp's `goal` tool declares no approval tier and falls back to `exec`, so under the desktop's `--approval-mode=write` every agent call to it (`get`, `complete`) asks "Allow tool: goal" (reported upstream as omp #14368; `todo` and `ask` declare `read`). The approval card's session/project rule is the workaround.
- The token budget is set at `create` only; changing it is terminal-only in omp.
