# Browser panel

One desktop tab owns one headless Chromium, shared by its omp agent and the browser panel. Rust owns the choice of browser, the process, the CDP connections, page selection, the screencast and the annotation overlay. The app webview only paints images and forwards input: browser pages never load in it.

Chromium opens no debugging port: `--remote-debugging-pipe` is its only CDP endpoint, and only the app holds the pipe. The broker gives every client — the panel's view and each agent WebSocket — a session of its own on it (`Target.attachToBrowserTarget`, or `Target.attachToTarget` for a `/devtools/page/<id>` client), which the client addresses without a `sessionId`: the broker adds that root session on the way to Chromium and removes it on the way back. A client is registered by the pipe reader as it routes the attach reply, so a detach right behind it (a page closing at that moment) ends the client at once. Every client command goes out under an id the broker allocates (from the counter of its own root calls) and comes back under the client's own id, so a reply Chromium sends without a `sessionId` (an unknown or just-detached session, a malformed command) still reaches its sender, never a broker call. Sessions a client attaches itself (an attach reply, a `Target.attachedToTarget` event on a session it owns) are its own and pass unchanged; a command naming any other session is answered with Chromium's "Session with given id not found." error and never sent, and so is one over `MAX_COMMAND` (100 MiB less 64 KiB: Chromium ends the whole pipe on a message over 100 MiB). Commands go out through one writer thread fed by a bounded queue (64 MiB), so no client blocks on the pipe; replies and events come in on one reader thread into each client's own queue, also bounded (64 MiB besides the message at its head); a client that falls that far behind is cut and its sessions detached, so a stalled agent never holds up the panel. Both threads hold the broker weakly: the broker closes when the last owner drops it, and Chromium owns it while it runs. The panel's view is a broker client like the agent's, not a proxy connection, so its own input and screenshots do not look like agent intent to the tap.

## Which Chromium

The browser is a Rust-owned setting, like the terminal's shell: `<app config>/browser.json` `{ "path": "" }`, stored through `program_setting` (file, lock, cache and refuse-to-overwrite policy; `process/settings.rs` is the browser's view over it). The webview never sends a path for a launch and keeps no copy. Settings → Browser shows a `chromium` row (`design/settings/rows-programs.jsx`) whose menu lists `automatic` (with what discovery finds now), every browser discovery finds, the stored path when it is none of them, and "other…":

- `browser_settings()` → `{ path, automatic, installed, error }` (`path` `""` = automatic; `error` when the stored path is no longer an executable file).
- `browser_set_path(path)`: trims, drops one pair of surrounding `"` (Windows "Copy as path"), stores `""` or an absolute path to an executable file (`program_setting::is_executable_file` / `typed_path`, shared with the terminal's shell); a macOS `.app` bundle stands for `Contents/MacOS/<name>`.
- `browser_pick_path()`: native file dialog in Rust (as `terminal_pick_shell`), stored as above; `null` = cancelled.

`Slot::ensure` reads the setting at every launch, so a change applies to the next Chromium a tab starts; a running one is not replaced. A configured path that no longer works is a launch error (the panel channel's `state` message `error`, HTTP 503 to the agent), never a fallback to another browser.

Automatic discovery (`process/locate.rs`, a pure function of the platform and its places, so every platform's order is tested on any host):

- **Linux:** real browser binaries first (`/opt/google/chrome/chrome`, `/usr/lib/chromium/chromium`, `/usr/lib/chromium-browser/chromium-browser`, `/usr/lib64/chromium-browser/chromium-browser`, `/usr/lib64/chromium/chromium`, Chrome Beta/Unstable, `/opt/microsoft/msedge/msedge`, `/opt/brave.com/brave/brave`), then omp's Chrome for Testing, then the PATH launchers (`google-chrome`, `google-chrome-stable`, `chromium`, `chromium-browser`, `microsoft-edge`, `brave-browser`) last. Launchers are distro scripts that inject the user's own flag files; Chrome for Testing goes after the installed browsers because Ubuntu 23.10+ refuses it a sandbox and the desktop keeps the sandbox on. A candidate that resolves into `/snap/`, to the `snap` binary, or is a small `#!` script mentioning `/snap/` is skipped: snap confinement keeps it out of the hidden cache folder its profile lives in. The skip reason is part of the "no Chromium found" error.
- **macOS:** Chrome for Testing first, then Google Chrome, Chromium, Edge, Brave, Chrome Beta and Canary under `/Applications` and `~/Applications`.
- **Windows:** Chrome for Testing first, then Chrome, Edge, Brave, Chromium and Chrome Beta under `%ProgramFiles%`, `%ProgramFiles(x86)%` and `%LOCALAPPDATA%` (per-user installs).

Chrome for Testing builds come from omp's puppeteer cache, newest version first: `$XDG_CACHE_HOME/omp/puppeteer/chrome` when that `omp` folder exists (not on Windows), then `~/.omp/puppeteer/chrome`. Each file is tried once even when several names reach it. When the home folder cannot be resolved, the home-based candidates (`~/.omp/puppeteer`, macOS `~/Applications`) are skipped; there is no stand-in such as the temp dir, where another account could plant a browser. The app does not download a browser.

A launch tries the candidates in order, at most three: a binary that cannot run, exits or closes its debugging pipe before answering on it makes way for the next; a timeout or a pid-file failure stops the attempt. The error lists every attempt with the last 2 KiB of its stderr (`process/stderr.rs`; a thread drains the pipe for the browser's whole life): a line cut at the window's front is dropped, unless it is the only one (a last line longer than 2 KiB), which is shown clipped.

## Placeholder port, overlay and lazy launch

`start_session` allocates a browser entry before spawning omp. Allocation binds `127.0.0.1:0` and exclusively creates `<app cache>/browser/<pid>/<session_id>.yml` containing only:

```yaml
browser:
  cdpUrl: "http://127.0.0.1:<placeholder port>"
  relay: false
```

`relay: false` because omp ranks an enabled browser relay above `cdpUrl`; without it a user with the relay on would drive their own Chrome, not the panel's browser. omp's Tern setting ranks below `cdpUrl` and needs no override.

`agent/spawn.rs::omp_args` appends the single token `--config=<path>` **last**, after profile/resume/cwd and `--approval-mode=<mode>` (the mode `ApprovalModeStore::resolve` picked). Preserve this overlay order and its browser-only contents: the tab must use the managed endpoint without replacing its normal profile settings or changing approval policy.

Allocation does not launch Chromium. The first admitted proxy request or `browser_open_panel` calls the tab's `Slot::ensure`. Its per-tab lock prevents duplicate launches without blocking other tabs. The placeholder port stays stable across Chromium restarts. Launch failure returns HTTP 503.

Only an app run without managed browsers at all (no cache dir: `BrowserManager::unavailable`, logged once at startup) starts omp without the overlay; omp then uses its own browser configuration and the panel has none. A tab whose own allocation fails (a respawn racing the tab's close: "still closing", the port or overlay failing) fails `start_session` (`allocate_if_available`), and the frontend's rollback closes the tab: it never runs silently without its browser.

## Proxy admission and routing

The placeholder port is loopback TCP, which every account on the machine can reach, so every connection is checked first, on its own connection thread and before its request is read: `proxy/peer.rs::same_user` serves only a socket owned by the OS user the app runs as, and closes anyone else's unanswered. At most 8 checks run at once (`MAX_PEER_CHECKS`); a connection that finds none free is closed unanswered, so a flood cannot pile up checks. Only a connection that passed waits in the head queue (`MAX_UNVETTED`), so another user's sockets never displace the agent's. The check reads the kernel's socket tables, finding the client's end of the connection (local = the peer's address, remote = the proxy's):

- **Linux:** `/proc/net/tcp` and `/proc/net/tcp6` (a v4-mapped client address counts as IPv4); the client row's `uid` must equal the `uid` of the proxy's own row of the connection.
- **Windows:** `GetExtendedTcpTable(AF_INET, TCP_TABLE_OWNER_MODULE_CONNECTIONS)` gives the client row's owning pid and the time the socket was bound (`liCreateTimestamp`; a row without one is refused). That pid is the process that bound the socket, which may have exited and had its pid reused, so the process now holding the pid must have been created no later than that time (`GetProcessTimes`); then its token user SID must equal the app's (`OpenProcess` + `OpenProcessToken` + `GetTokenInformation(TokenUser)` + `EqualSid`). The app's own pid goes through the same time check, with its own creation time and SID cached. A process whose token cannot be opened (an elevated agent behind a non-elevated app, say) is refused.
- **macOS:** `/usr/sbin/lsof -nP -a -iTCP@<peer> -sTCP:ESTABLISHED -Fpun` (absolute path, 5-second cap) must list `<peer>-><proxy>` held by a process whose uid is the app's `geteuid()`. A non-root `lsof` sees no other user's sockets, so absence is a refusal.
- **Any other OS:** refused.

omp connects from its own process (its tab workers are Bun worker threads), so the agent always passes. Then `proxy/http.rs::admit` vets the request head before anything launches; a refusal is HTTP 403 and never calls `ensure`:

- an origin-form request target (starting with `/`);
- well-formed header lines and exactly one `Host` naming `127.0.0.1`, `localhost` (case-insensitive) or `[::1]`, with an optional numeric port (DNS rebinding);
- no header only a web browser sends: `Origin`, or any `Sec-Fetch-*` header except `Sec-Fetch-Mode` on its own (Node's `fetch` sends that one, and puppeteer may run there; a browser always adds `Sec-Fetch-Site` too);
- outside `/json*`, an `Upgrade: websocket` request.

The admitted request is routed before anything launches as well (`proxy/mod.rs::route`): an unknown path is a 404, a malformed upgrade (not a GET, no `Sec-WebSocket-Key`, a version other than 13) a 400. Discovery is answered from the broker's root session (`proxy/discovery.rs`), since Chromium serves no HTTP:

- `GET /json/version`: `Browser.getVersion` as `Browser`, `Protocol-Version`, `User-Agent`, `V8-Version`, `WebKit-Version`, with `webSocketDebuggerUrl` = `ws://127.0.0.1:<placeholder port>/devtools/browser/<broker id>`;
- `GET /json`, `/json/list`: `Target.getTargets` without `browser` and `tab` targets, each with `webSocketDebuggerUrl` = `ws://127.0.0.1:<placeholder port>/devtools/page/<targetId>`;
- `PUT /json/new?<url>` (`Target.createTarget`, `about:blank` by default; a GET is a 405 as in Chrome), `/json/activate/<id>`, `/json/close/<id>`;
- anything else under `/json` (`/json/protocol` included) is a 404, and so is `/json/activate/<id>` or `/json/close/<id>` for a target Chromium does not know ("No such target id: <id>", as Chromium answers). Another refused broker command is a 502, a browser that went away a 503.

A WebSocket upgrade to `/devtools/browser/<any id>` becomes a browser-level broker client, one to `/devtools/page/<targetId>` a page-level one; the proxy answers the handshake itself (`proxy/ws.rs`, no extensions negotiated) and pumps text messages both ways until either side ends. A binary frame that is valid UTF-8 is forwarded as text; any other closes the connection with 1003. A message or frame over `MAX_COMMAND` fails that connection alone. At most 32 admitted connections are served at once: a 33rd admitted request gets a 503 on its own connection thread, after `http::admit`. Separately, at most 32 connections may wait for their request head (`MAX_UNVETTED`); when one more arrives, the one that has waited longest is cut, so idle or unvetted sockets (a web page's preconnects, say) never hold the slots the agent needs.

## Launch flags and environment

`process/launch.rs` starts Chromium with:

- `--headless=new`: rendering without a separate browser window.
- `--no-startup-window`: suppress Chromium's automatic startup page. After `Browser.getVersion`, launch creates one `about:blank` through `Target.createTarget` before exposing the broker. Both requests share the launch deadline.
- `--remote-debugging-pipe`: CDP over a pipe pair only the app and Chromium hold (`process/pipe.rs`), no port; the pipe ends with Chromium. On Unix Chromium reads fd 3 and writes fd 4: the child's ends are moved there between fork and exec, and are close-on-exec everywhere else; on macOS std's `io::pipe` sets close-on-exec only after creating a pipe, so `attach` creates both under the exclusive spawn gate. On Windows they are named by `--remote-debugging-io-pipes=<read handle>,<write handle>`, so they must be inheritable while Chromium's process is created, and Windows hands every inheritable handle to every child created with handle inheritance (what `std::process::Command` always asks for). So no other child is created in that moment: every spawn in the app holds the spawn gate (`src-tauri/src/spawn_gate.rs`) shared, and `CdpPipes::spawn` holds it exclusively from making the ends inheritable until it has closed them after the spawn. The gate prefers spawns: a launch waits until none is in flight (a long git browser read included), but while it waits new spawns still start; only the launch itself shuts them out, for milliseconds. `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` would not do instead: it narrows only the `CreateProcess` call it is passed to, std offers attribute lists on nightly only, and gix's own spawns would pass none. A process started outside the gate (third-party code inside the app) could still hold the pipe ends, so the end of Chromium's stderr also closes the broker (`process/stderr.rs` drain callback): std's own spawns never inherit another child's stdio. Launch readiness requires both version and initial-page replies within the same 10-second startup timeout; a binary that exits, closes the pipe or answers with an error first makes way for the next candidate, and one that exited is reported as "exited early (<status>)" even when the pipe broke first.
- `--user-data-dir=<private throwaway profile>`: no reuse of the user's normal browser profile.
- `--no-first-run`, `--no-default-browser-check`, `--disable-background-networking`: suppress first-run/default-browser flows and background browser networking, not page networking.
- `--disable-extensions`: no extension, not even one a launcher's flag file or a managed policy adds.
- `--disable-features=BackForwardCache`: a page restored from the back/forward cache would keep the annotate overlay's isolated-world state without a new execution context. It is the only `--disable-features` flag: Chromium honours only the last one.
- `--window-size=1280,800`: initial size; opening/resizing the panel applies CDP device metrics with its CSS width, height and DPR.
- `--use-mock-keychain --password-store=basic`: keep this disposable profile away from the OS keychain/keyring, avoiding repeated macOS “Chromium Safe Storage” prompts. This is not an encrypted persistent credential store.

Only when the candidate is a `#!` script (a distro launcher: the PATH launchers, or a launcher script picked in Settings) does the child get a private `XDG_CONFIG_HOME` (`<profile>/xdg-config`, empty) and lose `CHROME_USER_FLAGS` / `CHROMIUM_FLAGS`, so the launcher finds none of the user's `*-flags.conf` files or flag variables. Real binaries (Chrome, Chromium, Chrome for Testing, Edge, Brave) read neither and keep the user's environment, so fontconfig and dconf/GSettings proxy settings still apply. Child PATH resolution uses `child_path::apply_child_path`; process-tree supervision uses the same process-group/Windows Job Object machinery as agent children. No `--no-sandbox` flag is added.

## Agent-follow: intent, not attachment

Each agent proxy connection has a read-only tap. For a page-level WebSocket it knows the target from `/devtools/page/<id>`; for a browser-level connection it maps flattened `sessionId` values to page `targetId` values from attach replies/events. Non-page sessions are excluded when identified by the event.

Follow signals are `Target.activateTarget`, successful `Target.createTarget`, `Page.navigate`, `Page.reload`, `Page.navigateToHistoryEntry`, `Page.bringToFront`, `Page.captureScreenshot` and `Input.*`. **Attachment is bookkeeping, not intent**: Puppeteer can remain attached to every page, so following `Target.attachedToTarget` or an attach reply would pick arbitrary pages rather than the page the agent actually uses.

The entry remembers the last reported target even while the panel is closed. Opening starts there if it still exists, otherwise on the newest discovered page (creating `about:blank` if needed). The user's own actions hold the view for five seconds: picking, opening or closing a page tab, address-bar navigation, back/forward, and any panel input except pointer moves. While held, the newest agent report is kept and shown when the hold ends; the decision is re-checked under the switch lock, so a tab the user picks meanwhile wins. A report for a page not listed yet waits for its discovery; a closed page is dropped. Annotate turns off whenever a follow actually shows the agent's page — on the report, when a held report is shown at the hold's end, and when a waited-for page appears — so annotate turned on during a hold is turned off when the held follow fires (the user's picks would land on a page the agent is changing).

The connection's two pump threads (`proxy/ws.rs`) push each message to their direction's `Feed` **before** forwarding it, as the agent sees it (decoded WebSocket text toward the broker, the broker's messages with the root session already removed toward the agent). `Feed::push` queues only a message under the size cap (commands 1 MiB, replies/events 64 KiB) and passes a bigger one without copying it, with one exception: a server message starting `{"method":"Target.attachedToTarget"` is read up to 1 MiB, since it carries the page's full URL and title and is the only place an auto-attached session is named. Both directions share one queue (at most 1024 messages and 4 MiB per connection), so commands, replies and the commands depending on them reach the observer in causal order. JSON parsing and the follow callback run on a separate observer thread that the pumps **never wait for**. A full queue or an error from the tap (too many sessions, say) disables tapping for that connection and logs why; forwarding continues unchanged. The tap must never block or alter what is forwarded.

## View, frames and input

A view is one browser-level broker client (its own browser session on the tab's pipe) with `Target.attachToTarget { flatten: true }`. It discovers page targets and attaches to the page being shown. A switch releases the old overlay, stops its screencast and detaches it, then enables the new page and installs its overlay; a failure after the attach (`Page.enable`, viewport, screencast) sets `state.error` ("cannot show the page: …") instead of leaving a frozen frame, and leaves the tab not shown, so picking the same tab again (or a follow to it) retries the whole switch. `state.error` is cleared by the next switch that works or a main-frame navigation; a closed view's final `idle` state carries `error: null`. When the last page closes and its blank replacement cannot be created, `state.error` is "cannot open a page: <reason>". `tab_activate` / `tab_close` refuse ids not in the view's page list ("no such tab"). Page titles are refreshed with `Target.getTargetInfo` after a switch and on `Page.loadEventFired` / `Page.navigatedWithinDocument`, so a tab shows the document title, not the URL it had when the navigation committed.

Viewport changes restart JPEG screencasting (quality 70): the device metrics are set first and only then is the screencast stopped and started, so a refused size leaves the running screencast alone. A frame of the wrong size asks for a heal restart (one at a time, at most 5 in a row, 300 ms apart, the budget refilling after 5 s); a restart that fails is retried up to 4 times. While a page commits a navigation to a new document, Chromium refuses its commands for a moment ("Not attached to an active page"; the command did not run): `Core::call` sends such a page command again, up to 6 times 50 ms apart, so back/forward, a switch or a resize right after a navigation still lands, and the history is asked again once the page stopped loading. The panel size is validated before Chromium is launched for it: 1–8192 CSS pixels per side, DPR 0.25–8, at most 8192 device pixels per side. A resize reads the shown page and the size under the switch lock (`Core::resize_shown_page`), so a resize racing a switch goes to the new page.

**Panel channel** (`view/emit.rs`): `browser_open_panel` takes a Tauri `Channel` from the webview, and everything the view reports during that open goes over it, in order: `state`, `tabs` and `pick` as JSON `{ type, value }`, frames as raw bytes. A frame is a 16-byte little-endian header (`seq` u64, `cssW` u32, `cssH` u32) followed by the JPEG, decoded from Chromium's base64 once in Rust on the emitter thread, so the webview parses no base64 or JSON per frame (large payloads reach it through Tauri's channel fetch, as an `ArrayBuffer`). One channel per open replaces per-kind event listeners: there is no listen/unlisten race on open or close, and a page's `tabs` message precedes its frames because both share the channel's order. The reader passes CDP event params by value, so a frame's base64 moves from the broker's outbox to the emitter without a copy. Every open (and every close) advances the panel's generation (`browser/commands.rs`), so the newest open wins: from the moment a newer open starts, an earlier one still in flight emits nothing more (no `running`, tabs, frames or closing `idle`) and is refused with "panel reopened" when it finishes; an open installs its view only if no close or newer open came in between.

**Frame flow control** (`view/frames.rs`): every frame carries a per-view `seq`. At most one frame is in flight to the webview; the newest frame waits in a one-frame slot and replaces an older waiting one. Chromium's `Page.screencastFrameAck` is sent only once the webview acks the frame it holds (`browser_frame_ack { sessionId, seq }`, synchronous and cheap) or after a 1-second timeout, so a busy webview slows Chromium down instead of queueing frames, and a lost ack costs a second, not the stream. Skipped frames are acked to Chromium on the next release. Emitting a frame takes a dedicated emit-order lock (also held while a switch publishes its tabs), never the view's model lock while decoding or sending. Activation generations reject old-page frames and queued input after a page switch.

`browser-screen.js` decodes JPEGs with `createImageBitmap`, decodes only the newest frame and paints on a DPR-sized canvas. Every frame is acked exactly once: after it was painted, or when it was dropped (superseded before decode or paint, undecodable). Frames carry the page CSS dimensions they show; marker geometry is published with the bitmap actually painted. A size reaches Rust once it held for 100 ms, from a `ResizeObserver` or a `matchMedia` resolution query (moving the window to a display with another scale). Pointer coordinates map through frame CSS dimensions rather than canvas backing pixels. Mouse moves and wheel ticks are coalesced to one of each per animation frame (wheel deltas add up), mapped to page coordinates when they go out, and flushed before a press/release; side buttons 3/4 are `back` / `forward`. Rust's synchronous `browser_input` only queues work, preserving IPC input order: at most 512 events not yet handed to the broker (`INPUT_QUEUE`); beyond that input is refused ("browser is busy"), which means the input thread is behind, not that the page hangs. The input thread posts each event without waiting for Chromium's reply (CDP keeps a session's order), so input is not capped at one event per round trip. Other commands run blocking CDP work off the IPC thread. Commands whose reply nothing reads (stopping the old screencast, detaching, `activateTarget`, focus emulation, the overlay's `Runtime.enable` and binding) are sent without waiting as well. `loading` follows the shown page's main frame only (its frame id is the target id); subframes loading do not flip it. Refreshing a frame (annotate toggle, after a capture) restarts the screencast without re-applying the viewport.

`browser_navigate` loads only `http://`, `https://`, `data:` and `about:blank` URLs (Rust's allowlist, matching the address field's `normalizeUrl`; both refuse control characters, Unicode Cc, also inside a `data:` URL); anything else is "unsupported url scheme". It returns once `Page.navigate` is sent: a slow server is not a failure, and a failed load shows as `state.error` ("could not load <url>", from `frameNavigated`'s `unreachableUrl`) until a later navigation succeeds.

The panel (`design/browser-panel.jsx`) shows Rust's `state.error` whatever the status. While the browser is not running (starting, stopped, error) it is the full overlay over the view, the error text in place of the generic status (a lost connection reads "browser connection lost", not "browser stopped — reload to restart"), with the reload button when stopped or failed. While it runs (a failed tab switch "cannot show the page…", a failed load "could not load <url>") it is a strip along the bottom of the page that the pointer passes through, so the page stays usable, until Rust clears the error.

Keyboard focus sits on a hidden `<textarea>` (`.browser-sink`) inside the view, so paste, IME composition and dead keys work: keys that type nothing go out as CDP key events, composed text, dead-key characters and pastes as `{ kind: "text" }`. Ctrl/⌘+V and Shift+Insert (without Ctrl, Alt or Meta) paste natively into the sink. Logical letter keys determine virtual key codes on non-US layouts; AltGr (`getModifierState("AltGraph")`) types its character and drops the Ctrl/Alt bits. Which keys leave the page for the app is the terminal's rule, `OMP_KEYMAP.guestShouldBypass` (`app/keymap.js`): a chord bound to a global action marked `fromGuest` (`desktop.browser.toggle`, `desktop.terminal.toggle`, next/previous tab), a `super` chord, or off macOS a `ctrl+shift` chord goes to the app; plain `ctrl+<key>` / `alt+<key>`, unbound chords, the copy/paste chords and AltGr characters stay with the page. Esc while annotating is the panel's: it closes the comment popover first, then leaves annotate mode, and is always prevented, so the keymap's interrupt never fires from the panel; outside annotate mode Esc goes to the page. The address field's Esc (discard the edit, blur) is prevented too, so it never interrupts a running turn. An Esc that ends an IME composition is left to the IME everywhere: on the page, in the address field and in the comment popover; it neither cancels a pick nor leaves annotate mode. Each mouse button's release is tracked on its own, so releasing a second button does not swallow the first one's release. `useBrowser` hands its channel handler to `browserOpenPanel` (the backend's first `state` message arrives during the open), queues initial URL/resize requests until opening settles, and disposes the screen, bitmaps and the view when leaving the panel or switching desktop tabs; messages of a channel it no longer owns are dropped. A refused `browser_input` (no page shown) is logged at most once a minute per open panel.

## Annotation overlay and binding contract

`annotate/` installs `overlay.js` **per attached page session**, not just once per browser. `Runtime.addBinding` exposes `__ompAnnotate` only in the isolated execution-context world named `omp-annotate`. `Page.addScriptToEvaluateOnNewDocument` uses that world and `runImmediately: true` for the existing document and future navigations. Context-created events apply the current annotate flag; release forgets contexts and turns the overlay off before detach.

Turning `set_annotate` on installs the overlay on the shown page first and fails if that fails; turning it off clears the flag first and evaluates the page's contexts only when there is a page, so it fails only for a closed view. Either way the flag change and the `__ompAnnotateSet` evaluation of every `omp-annotate` context of the shown page (frames included) are sent under the annotate lock, like a release, then one blocking round trip precedes the screencast refresh: a concurrent close or toggle is always sent after them, so the page ends with the final flag. The flag is reported in the panel channel's `state` message as `annotate` (Rust's truth; the toolbar shows it; a closed view reports `false`, and a toggle a close overtook does not report it afterwards), and every toggle forces a fresh screencast frame so no stale hover outline stays on screen. A pick whose binding call arrives after annotate was turned off is dropped (`pick.rs` checks the flag under the lock when it emits).

The script uses a closed-shadow overlay host in the top document and installs capture-phase pointer/mouse listeners (including enter/leave). In same-process subframes it installs the same capture-phase swallowing listeners (pointer, mouse, click, dblclick, auxclick, contextmenu, enter/leave) and follows the annotate flag, but builds no overlay and reports no picks: drawing and picking stay in the top document. Annotate mode suppresses page click/hover handling but leaves scrolling and keys available. Only trusted events are swallowed: a page script's or the agent's `el.click()` still reaches the page. A left click picks an element; a drag over four CSS pixels picks an area (a drag with a side under 1 px becomes an element pick). Rendering must stay **CSSOM-only** (`element.style`, `textContent`): no style elements, inline-style attributes or HTML strings. This keeps the overlay working with strict page CSP and Trusted Types.

`__ompAnnotate(JSON.stringify(payload))` carries:

- `kind`: `element` or `area`.
- `rect`: viewport CSS pixels `{ x, y, w, h }`; `docRect`: the same box plus page scroll at pick time (required).
- `url`: page URL.
- Element-only `selector`, `tag`, `html`, `text`; areas carry null element fields.

Selectors prefer a unique escaped id, then unique `data-testid`, then at most six ancestor segments. Names use `localName` (SVG elements keep their case); tags and classes are CSS-escaped; `:nth-of-type` disambiguates same-tag siblings still matched by the tag/class segment. HTML/text are bounded to 20,000/500 UTF-16 units, URL/selector/tag to 8192, without splitting surrogate pairs (`toWellFormed()` where available). Rust accepts only the named binding from a tracked isolated-world context of the active page, and only within two seconds of a mouse release the panel itself sent (`panel_released_within`), so agent input never becomes a user pick. It bounds the JSON payload to 256 KiB and the fields, and rejects invalid/non-finite rectangles, areas under 1 px or unknown kinds. Page scripts cannot directly call the isolated binding, but DOM content remains untrusted.

`browser_capture` takes the pick's `docRect` and only works on the document the last pick came from: after a navigation or page switch it fails with "the page changed since the pick". It hides the overlay **visually only** (`__ompAnnotateHide`, counted, so concurrent captures each hide and show it; annotate stays on and clicks stay swallowed) in the pick's isolated context, which also returns scroll, viewport size and device pixel ratio (the page cannot spoof them there). The clip is `docRect` cut to the visible viewport (an empty result is an error), scaled so its longest side stays within 2000 device pixels (`OMP_IMAGES`' edge cap). The overlay is shown again whatever the outcome; a failed show does not discard a good shot. A failed capture still permits a text annotation and shows a failure note. The comment popover opens below the pick, else above it, else pinned inside the view (`OMP_BROWSER.popoverTop`), and is never taller than the view. It belongs to annotate mode: whatever ends annotate mode (the toolbar button, the agent acting on the page, closing the panel or switching tabs) closes it and discards its pick, and turning annotate on again brings no old popover back. Chips retain `docRect` for scrolling back to the pick when the panel still shows the same URL.

## Panel, links, chips and the prompt

The panel takes the column beside the chat, which `app-live.jsx` keeps per desktop tab as one value: the rail, the conversation tree or the browser (`side`). The stage layout, the widgets' `railVisible`, the tree's fetching and `useBrowser`'s `open` all derive from it, so opening one closes the other and a tab switch shows that tab's column. Leaving the browser leaves full view.

The desktop's local `/browser` (`OMP_BROWSER.browserCommand`) opens the panel; `/browser <url>` loads the address (one `normalizeUrl` refuses gets a "not a web address" chat note). It shadows omp's builtin `/browser [headless|visible]`, the mode switch of omp's own browser tool: the panel shows each tab's page itself, so `headless`, `hidden`, `visible`, `show` and `headful` get a chat note instead of loading `https://visible`.

A primary click on a chat link to `localhost`, `127.x.x.x` or `[::1]` (`OMP_BROWSER.linkClick`) opens it in the panel; with ⌘/Ctrl, Shift or Alt it goes to the system browser through the external opener. The markdown containers route it: their delegated click (`useMarkdownClick`, `ui/markdown.jsx`) runs the copy buttons, then the handler `MarkdownLinkContext` carries, which `app-live.jsx` provides as `browser.onChatClick` (null while Settings → Browser's `browserLocalhostInPanel` toggle is off).

Saved chips are per desktop tab, held by `useBrowser` (the panel draws their markers on the page they were picked from). A chip's screenshot goes through `OMP_IMAGES.normalizeImage` like a pasted image. Chips go out with a submit like the rest of the composer's draft: `app-live.jsx` takes them at once (`takeChips`: those ids; chips added meanwhile stay for the next message) and merges each chip's comment, URL, selector and bounded HTML into the send, steer, follow-up or goal delivery (`OMP_BROWSER.mergeIntoMessage`), adding their PNGs subject to the shared eight-image cap. Excess screenshots are reported, while annotation text still goes out. Like typed text and images, a delivery omp refuses is not handed back (a refused steer or follow-up shows the whole message in its failure note); a goal start omp refuses hands its draft back to the tab it was typed in: the chips go back to that tab (`restoreChips(chips, tabId)`) even when another tab is shown by then, the typed text and images into the composer only while that tab is still shown, and a tab closed meanwhile gets nothing. A goal stores only the typed objective; the chips ride in the objective's delivered prompt or steer (`goalStart`'s `prompt` argument, `docs/architecture/goal-mode.md`).

Where a submit goes is decided on the typed draft (`OMP_SLASH.routeSubmit`), before annotations merge in; a command carries no chips. Merging never changes that classification, so `live.js` `steer` / `followUp` classify the text they send as for any other caller. Page-derived fields are labeled as untrusted data and wrapped with `OMP_MARKDOWN.fenceCode`, using a backtick fence longer than any run inside those fields. `/skill:` tokens and line-leading slash commands are escaped in the page fields and in the user's comment (which stays outside the fence) because omp's command parser does not honor Markdown fences. Every `@` in the page fields (URL, selector, tag, text, HTML) becomes `\@`, since omp reads each `@path` mention (at the start or after whitespace, a bracket, a quote or a backtick) into the turn regardless of fences; the user's comment keeps its `@`, which may be a real file mention.

## Lifecycle

- Startup prepares `<app cache>/browser/<pid>/`. Unix directories are created with `0700`, overlay and pid files with `0600` and exclusive creation (`instance.rs::create_private_file`); session ids are restricted before becoming filenames. The cache root and instance path must be real directories, not symlinks. A directory with the app's own pid that already exists is a crashed earlier run's: its browsers are reaped and it is recreated empty. Each launch attempt uses `profiles/<session_id>-<n>` and records its browser PID next to the profile as `<profile>.pid`, removed after reaping.
- Dead instances are pruned on a `browser-prune` thread at startup (`BrowserManager::prune_stale_instances`), never on the main thread. A directory is dead when its pid is not alive (`supervisor::pid_is_alive`: `kill(pid, 0)` on Unix; on Windows `OpenProcess` + `GetExitCodeProcess`, where only "no such pid" counts as gone and a process that cannot be opened for any other reason, such as access denied, counts as alive); other live instances and non-pid names are left alone. On macOS/Linux the recorded browsers are reaped first: a PID is targeted only if it is alive, its command line contains `--user-data-dir=<profile path>` bounded by start/end, NUL or ASCII whitespace, and it leads its own process group and that group is not the app's own (`supervisor::kill_group_if_leader`, which then SIGKILLs the group). Linux reads `/proc/<pid>/cmdline`, accepting both NUL-separated argv and Chromium's rewritten space-joined process title; macOS reads `/bin/ps -o command= -p <pid>`. Cleanup waits up to two seconds for the leader to disappear; if it remains alive, the directory is retained rather than deleted under a running browser. On Windows the Job Object already killed every browser of a dead process, so its directory is removed directly.
- Profile and instance removal retries on Windows (10 × 100 ms) while a killed Chromium's helper processes still hold files: profiles, dead-instance pruning, shutdown, and the startup removal of a leftover own-pid instance directory.
- Closing the panel or switching desktop tabs ends only the view. Browser pages continue running; the tab's side column and chips remain per tab in React memory.
- An omp profile switch or approval-mode restart respawns the agent with the same tab overlay and browser. `stop_session` must not release Chromium.
- After a Chromium crash the view reports stopped. Panel reload/reopen or the next agent connection launches a fresh throwaway profile behind the existing placeholder port; old page state is lost.
- Desktop-tab close calls `live.js::_closeTab` / `close_tab`; reload cleanup uses `close_all_tabs`. Both release each tab's browser as well as its agent, widgets, git watcher and terminal. Only `close_tab` / `close_all_tabs` and app-wide `kill_child_processes` end a tab's browser. Release marks the slot closed, closes the view and proxy sockets, waits out an in-flight launch, kills/reaps Chromium's process tree, and removes its profile and overlay. Concurrent release callers wait for teardown; shutdown includes releases already in flight. `close_all_tabs` releases its tabs' browsers side by side (`release_many`), and browser teardown runs alongside the terminals' hang-up grace (`lib.rs` `end_tabs`).
- `BrowserManager::Drop` calls `shutdown_all`, which tears every entry down in parallel (app exit waits for the slowest teardown, not their sum) and removes this process's `<root>/<pid>` directory. App exit and updater relaunch explicitly call `kill_child_processes`, killing agent trees first, browsers second, widget plugins third and terminal shells last; these paths cannot rely on managed-state destructors running.

## Security model and known limits

Chromium opens no debugging port: its only CDP endpoint is a pipe pair whose far ends only the app and Chromium hold, so no other process — another account's or the user's own, the app's other children included — can reach the browser except through the broker. On Windows and macOS that rests on the spawn gate (`spawn_gate.rs`): every child the app starts — omp, widget plugins, the terminal's shell, `git`, gix's own `git` and filter-driver runs (`gix::discover`, the git browser's reads), the external URL opener, other Chromium launches — is created under it. `clippy.toml` (`disallowed-methods`) rejects a spawn that bypasses it, but only in the local clippy run (`AGENTS.md`'s verify command); CI runs no clippy. A process started by third-party code running inside the app outside those calls (a shell extension in a native file dialog, say) is not covered. The agent-facing placeholder port is loopback TCP and so reachable by every account on the machine: the same-user check (`proxy/peer.rs`) closes every connection whose socket another OS user owns before its request is read, and fails closed when ownership cannot be established. It is not a per-process boundary: **any local process of the same user can use the placeholder port** like the agent (CDP itself has no authentication, and omp's puppeteer connection can carry no secret: it drops a `cdpUrl` path and sends no headers). Proxy admission keeps web pages out (loopback `Host`, no `Origin` or browser fetch metadata, WebSocket upgrades only outside `/json*`). Private files/profiles protect their filesystem contents. Do not expose or tunnel the placeholder port.

Agent actions still go through omp's normal tool approval flow under the tab's resolved `--approval-mode=<mode>`: with `yolo`, the agent's browser actions run without asking. The desktop proxy does not approve, filter or reinterpret tool calls. Manual panel controls are direct user actions, not agent tool calls. Chromium executes remote pages separately from the Tauri app webview: the webview receives image frames and bounded pick metadata, never page scripts. Pick HTML is prompt text, not app markup. Screenshots, DOM snippets and URLs may contain sensitive page data; sending an annotation intentionally includes that data in the agent prompt.

Limits:

- **The agent drives the page you see.** omp treats a `cdpUrl` browser as a borrowed, user-driven one: it never opens a tab of its own there and works in the visible page, so its navigation replaces the page you were on. Nothing in the desktop can give it a separate tab.
- One Chromium per desktop tab that used the browser, running until that tab closes: no cap and no idle shutdown.
- omp waits 5 seconds for the CDP endpoint, while a cold Chromium launch may take up to the 10-second startup timeout; a slow first launch can fail the agent's first browser call, and the next one finds Chromium running.
- An explicit `app.relay` / `app.tern` / `app.cdp_url` in a tool call and the `PI_BROWSER_RELAY` environment variable still outrank the overlay: the agent then drives a different browser than the panel shows.
- Requires a compatible installed Chromium-based browser or omp's Chrome for Testing; snap and flatpak packages are not candidates. No bundled browser or downloader.
- Fresh profiles mean no normal-browser cookies/logins/extensions and no browser-state persistence across tab close, crash or app restart. A browser configured in Settings that is itself a wrapper script still runs whatever that script adds. Pending annotation chips and panel-open state are in-memory only.
- Headless screencast/input is not a native browser surface: no native browser chrome, file-picker/download management or audio forwarding. Text input arrives as plain text (paste, IME and dead-key results).
- Annotation targets are the top-level DOM, not elements inside iframes or shadow roots. Cross-site (out-of-process) iframes are not covered at all: the view does not attach their targets, so clicks inside them still reach the page while annotating. Selectors are bounded best-effort hints; page mutation can invalidate them.
- Saved boxes are snapshots, not live DOM tracking. Markers use pick-time viewport coordinates and match by URL; chip scrolling uses pick-time document coordinates only on the currently shown matching URL, without reopening a page or selecting its original target.
- Follow is limited to observed intent commands through the proxy. An observer stuck until the queue fills can disable it for a connection without affecting agent traffic (logged to stderr only). Local processes of the same user using the proxy are indistinguishable from the agent to the tap.
- An agent WebSocket has no idle timeout: a half-open connection keeps its threads and one of the 32 admitted-connection slots until the tab's browser is released (`Proxy::shutdown` cuts every live socket). A write to the agent that blocks for 30 seconds cuts the connection.
- macOS runs `lsof` for every proxy connection (typically tens to hundreds of milliseconds, capped at 5 seconds), at most 8 at once: a busy machine slows the agent's connects, not its traffic, and another account flooding the port can make the agent's connects fail while the flood lasts (its sockets are closed unanswered, never served).
- An agent WebSocket is pumped by two threads that share the socket under one lock: a client that stops reading while it sends a large command (a synchronous WebSocket library, not puppeteer) can stall both directions until the 30-second write timeout cuts it.
- Orphan identity checks cannot recover original argument boundaries from Linux's rewritten process title or macOS `ps` output. `--user-data-dir=.../s1-0 x` matches `.../s1-0` because space is a delimiter, unlike `.../s1-01` or `.../s1-0-other`. Generated session/profile basenames contain no spaces, but the OS-provided cache root (including a macOS home directory) can contain spaces; there is no enforced space-free full-path invariant. Matching includes any spaces inside the requested full path, but cannot distinguish a separate argument from a different profile path with an appended whitespace suffix. Reaping remains best-effort, not a guarantee of exact argv identity.
