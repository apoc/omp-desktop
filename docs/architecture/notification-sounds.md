# Notification sounds (#91)

A short sound when an agent needs the user or a turn finished, in any tab. The sounds are synthesised and played in Rust (`cpal`, already linked for the voice spectrum), so the app ships no audio files and the webview's media stack and autoplay rules play no part.

## Decisions

- **D1 Events.** Two cues, both read from Rust's tracker overlay in `live.js` `_applyAttention` (`agent://attention`; the same per-session entries `{ busy, asks, asksOpened, background }` the dock bounce uses), for every registered tab, background tabs included:
  - *attention*: a question opened in some session (`OMP_ATTENTION.newAsk(previous, next)`: the session's `asksOpened` rose; omp's ask tool, a tool-approval prompt, a form request);
  - *finished*: a session's entry went from `busy: true` to `busy: false` (entry present in both snapshots). A vanished entry (process exit, tab closed) is not a finish. An aborted turn counts as finished.
  - One snapshot plays at most one sound; attention outranks finished.
  - No sound for the first snapshot (`trackerLive` null) or the page's first `attention_snapshot` reply (`_applyAttention(snapshot, { bounce: false, sound: false })`): their state is not new. The busy-close re-read (`_refreshAttention`, `{ bounce: false }`) skips only the dock bounce: it can apply a newer revision before its `agent://attention` event arrives, and the event is then dropped as stale, so it must not swallow the cue.
- **D2 When.** Tweak `notifySound`: `"off"` (default; no new sound for existing users) | `"background"` (only while the window is not focused, `document.hasFocus() !== true`) | `"always"`.
- **D3 Which sound.** Tweaks `soundAttention` (default `"bell"`) and `soundFinished` (default `"chime"`): one of the catalogue ids or `"none"` (that cue stays silent). Catalogue, all synthesised from oscillators with a short attack and exponential decay, each under ~1 s: `chime`, `bell`, `pop`, `knock`, `rise`, `blip`. An unknown stored id reads as the default.
- **D4 Volume.** Tweak `soundVolume`, 0–100 (step 5, default 60; `OMP_NOTIFY_SOUND.VOLUME`, which the Settings slider reads, and `prefsFrom` parses a stored value the way the schema's slider `clamp` does). Rust scales each sound so the RMS of its loudest 200 ms equals `(v/100)^1.5` × a fixed target (≈ −16 dBFS at 100), peak capped at 0.95, so all sounds play equally loud (at 100 the peak cap holds pop slightly under). 0 plays nothing (the ▶ preview is disabled).
- **D5 Playback in Rust.** Measured on Linux: WebKitGTK's Web Audio needs GStreamer's `autoaudiosink` (`gst-plugins-good`, only an optional dependency of `webkit2gtk` on Arch); without it `AudioContext.resume()` rejects with `InvalidStateError: Failed to start the audio device`, and every webview also starts a context outside a gesture suspended. So the webview only sends `notify_sound_play { sound, volume }`; Rust validates the id against its catalogue (unknown → error) and clamps the volume, renders the tones at the default output device's sample rate and plays them through `cpal` on a short-lived thread that owns the stream (created and dropped there, like `voice_spectrum/capture.rs`). The newest sound wins: each call bumps a generation counter and plays on its own thread; a superseded sound goes silent and its thread drops its stream at once, so rapid picking in Settings always plays the last pick. No output device or a stream error → logged (`eprintln!("[omp-desktop] …")`), never a panic; the command returns as soon as the thread is spawned. The catalogue ids live in Rust (recipes) and in `notify-sound.js` (ids + labels); a Rust test scans the JS file so the two lists cannot drift.
- **D6 Settings.** Settings → Session, new group "Sounds": `notifySound` as a seg row ("Play sounds": off / in background / always); a custom row `sounds` (owns `soundAttention`, `soundFinished`; shown only when `notifySound` is not `off`) with one line per cue: a seg of `none` + the catalogue and a ▶ preview button; picking a sound previews it too; `soundVolume` as a slider row (shown only when not `off`). Preview plays regardless of `notifySound`'s focus rule.
- **D7 Prefs path.** `live.js` keeps the sound prefs next to `sessionPrefs`: initial from `OMP_TWEAKS_STORE.read()`, kept current by `OMP_BRIDGE.setSessionPrefs` (app-live already passes the whole tweaks object). Validation lives in the sound module (`prefsFrom`), not in `OMP_SESSION_PREFS` (booleans only).
- **D8 Custom sound files are out of scope.** The issue asks for them as a preference; they need a Rust-side file pick, read cap and decode path. Built-in synthesised sounds ship first.

## Code

- `src/app/notify-sound.js` (`window.OMP_NOTIFY_SOUND`, plain IIFE, loads before `live.js`): `SOUNDS`, `MODES`, `VOLUME`, `prefsFrom(values, defaults)`, `cue({ previous, next, focused, prefs })` → `"attention" | "finished" | null` (pure), `play(id, volume)` (the `notify_sound_play` invoke, rejection swallowed). Regression: `tests/test-notify-sound.mjs`.
- `live.js` `_applyAttention` plays `cue`'s sound; `setSessionPrefs` updates the prefs.
- `design/settings/rows-sounds.jsx` (`sounds` custom row).
- `src-tauri/src/notify_sound/`: `synth.rs` (catalogue, pure renderer), `mod.rs` (`play`: validation, newest-wins generation counter, playback thread); `lib.rs` `notify_sound_play` command.
