# Session model

One tab = one omp process. `lib.rs::setup` spawns nothing; the frontend reopens the previous run's tabs (see *Reopening tabs on relaunch*), and the session column renders `design/empty-workspace.jsx` whenever `sessions` is empty — at a launch with nothing to reopen and after the last tab closes. It is a welcome screen, not a launcher (opening projects is the sidebar's and toolbar's job): the start screen picked in Settings → Appearance (`startScreen` tweak: matrix rain, latent space, next token, agent loop, forward pass or attention, each a live preview tile there) behind an ASCII-art OMP-DESKTOP logo. The canvas host is `design/backdrops/backdrop.jsx` (`window.Backdrop`: sizing, scale factor, theme tokens re-read when the root's class or style changes, offscreen-art and `env.logo` helpers from `design/backdrops/art.js`, step loop paused while the canvas is hidden or out of view — the Settings tiles behind a project tab, the empty workspace under the Settings page; its header is the renderer contract), one renderer per screen in `design/backdrops/<id>.js` registers on `window.OMP_BACKDROP_RENDERERS`, and the pure rules live in `app/backdrops.js` (screen list, shared math, next-token) and `app/backdrops-{latent,orbit,neural,attention}.js` (`test-backdrops.mjs`) and `app/matrix-rain.js` (logo geometry, rain; `test-matrix-rain.mjs`). Each screen also draws the logo its own way through the renderer's optional `logo` hook (cell geometry from `OMP_MATRIX.logoCells`; without the hook the host paints the default glow glyphs): matrix letters flash where rain passes, latent letters are a cloud of embedding points, next-token types the logo in like code, agent-loop sweeps and flares it on turns and results, forward-pass builds it from neuron dots. Renderers paint only with theme tokens, so a theme or accent switch recolours the running screen; under `prefers-reduced-motion` the host paints a frozen frame instead of animating, plus any note filed while no tab existed (`workspaceNotes`, e.g. a failed "Open with").

Each tab also owns its **profile**: `omp --profile <id>` isolates auth/sessions/settings/caches under `~/.omp/profiles/<id>/`. The profile list lives in `<app config>/profiles.json` (`src-tauri/src/profiles.rs`); the reserved id `default` means *no* `--profile` flag, i.e. omp's own `~/.omp/agent`. Without an app config folder (`lib.rs` `config_dir`: unresolvable or relative) the list lives in memory for the app run, starting with just the built-in profile; there is deliberately no temp-dir fallback, since another account could plant a list there and pick the profile tabs start in. The same memory-only mode covers `open-tabs.json`, `recent-projects.json`, `keybindings.json`, `terminal.json`, `approval-mode.json`, `browser.json` and the `approval-rules/` grants: the app stays usable, it just remembers nothing past quitting. Rail widgets are the exception: without a config folder they are disabled (`widgets.md`), not run from memory. Ids are slugified at creation and immutable — rename changes the label only. A profile is fixed at spawn, so `OMP_BRIDGE.switchSessionProfile(id, profileId)` stops and respawns that one tab's process (its transcript is dropped with it); `saved_sessions` resolves its root per profile, so history/resume stay inside the tab's own tree. `delete_profile` only unlists — it never deletes `~/.omp/profiles/<id>/`, and `OMP_BRIDGE.deleteProfile` refuses ids still in use by an open tab (only the frontend knows the tab set).

`create_profile` also seeds `~/.omp/profiles/<id>/agent/models.yml` with a single keyless provider (`providers: {anthropic: {auth: none}}`, see `profiles::seed_bootstrap`) — RPC mode is non-interactive and omp exits at startup once no model resolves, so without the seed a fresh profile's tab would die before ever reaching `/login`. It never overwrites an existing `models.yml` (a re-created id, or a user who already wrote one, keeps theirs), and `clear_profile_bootstrap` removes it after a successful login, but only while the file is still byte-identical to what it seeded.

The same menu ticks one profile as the **startup default**, stored as `ProfilesFile::startup` — a *pointer*, not a reordering, since `normalize` pins the built-in entry first and ids are the join key for on-disk data. `None`/absent means the built-in profile. It governs any tab opened with no active tab to inherit from — including every tab at launch — and whose recent projects the empty workspace lists; `openSession` otherwise inherits the active tab's profile, and running tabs are never moved. The pointer is re-validated against the list on every load and inside every `mutate`, so deleting or hand-editing away the ticked profile degrades to the built-in one instead of dangling. `list_profiles` returns `{profiles, startupId}` in one payload so the menu can't render a checkmark against a stale default.

**Composer and plan mode are per tab too** (#28), but desktop-only state omp never sees, so they live in React rather than in the bridge snapshot: `app-live.jsx` keeps a `plans` map and `design/composer.jsx` a `drafts` map (text, attachments, collapsed pastes, prompt-history recall position, in-flight image count), both keyed by session id via `app/session-ui.js` (regression `test-session-ui.mjs`) and pruned when a tab closes. Both key on `activeProject.id` (the tab being rendered, `""` with none open — a no-op key). The `Composer` deliberately stays mounted across tab switches rather than being re-keyed: a remount would re-fire its `draftInsert`/`promptInsert` effects, and an image still being prepared must land in the tab it was pasted into (`addFiles` captures the id), not in whichever tab is active when it resolves. Purely visual state (caret, slash selection, mention list) is reset on a switch instead. Plan state is not reset by `/new` or a profile respawn inside the same tab. The column beside the chat is per tab the same way (`app-live.jsx` `sides`: the rail, the conversation tree or the browser panel; `docs/architecture/browser.md`).

**Voice capture** is exclusive to the active tab. Separate composer buttons control live conversation (`/live`) and draft-only voice to text; the other button is disabled while either mode is active. Dictation uses the profile's omp STT configuration and sends `dictation_start` with a unique capture ID; `dictation_state` and full-replacement `dictation_transcript` frames update its preview. `dictation_stop` flushes and returns text, while `dictation_end` may arrive before either response and is also terminal. The bridge accepts frames only for its active capture, queues each completed transcript once with its owning tab ID, and retains the queue across React snapshot coalescing and tab switches until the composer acknowledges it. The composer appends to that still-open tab's current draft with a functional update; it never sends the text or recreates a closed tab. If omp exits before a terminal frame, the last preview is retained with an error.

Switching tabs or opening Settings pauses live conversation and stops dictation first; closing a tab ends capture, and an omp restart stops dictation too. A failed stop leaves the microphone's tab visible. Pause uses native `live_stop` (no background audio), retains a `paused` snapshot and captions, and resumes only on an explicit action with `live_start`; it does not pretend the upstream transport survived. End closes audio without forgetting spoken history. An unexpected native end also retains resumable history and its error. Start cancellation waits for the start command's IPC handoff before sending stop, and process replacement invalidates pending replies. Voice to text and live conversation cannot run together. Regression coverage is in `test-live-voice.mjs` and `test-session-ui.mjs`. `dictation_start` first shipped in omp 18.13.2, the version floor.

Live voice meters display omp's RMS amplitudes as `20 * log10(amplitude)` dBFS on a −60 to 0 dBFS scale, with a near-full-scale warning above −6 dBFS. The UI shows bars only; numeric readings remain in the meters' screen-reader value text. Silence empties the bar; 0 dBFS fills it. This changes only the display, not microphone gain or voice detection. RMS frames carry no sample peaks, so these meters cannot diagnose clipping. Captions follow new turns and same-turn transcript updates; level-only updates do not reset their scroll position.

Each live start/resume fetches raw `get_messages`, not the desktop's trimmed display, then passes `OMP_LIVE_CONTEXT.instructions` as `live_start.instructions`. It preserves the native unified assistant/delegation contract and quotes visible chat text, tool results, compaction/branch summaries and earlier spoken discussion as historical data. Historical braces are escaped inside JSON strings before omp's Handlebars rendering; old template expressions cannot expand or execute. Failed history reads prevent audio startup. The complete escaped instruction template is capped at 12 KiB UTF-8, conservatively below AVAS's 16,384-token ceiling with headroom for native name expansion. Budgets include the fixed prompt, project, JSON metadata, commas and escaped Unicode/braces, not just raw history characters. Chat receives up to 8 KiB and voice up to 2 KiB of serialized rows, with a 2 Ki-character entry cap and additional byte-based truncation where needed. Saved intent, the original objective and the latest turn get reserved space so oversized anchors cannot crowd out recent discussion; omissions/truncation are explicit. Images/audio and private thinking are excluded. Captions retain at most 100 entries of 8 Ki characters; a per-call turn offset prevents native role-local turn numbers resetting on reconnect from overwriting earlier captions. Voice memory is per current conversation in an open tab: new conversation/branch/fork/profile change clears it, while same-conversation process replacement preserves it. It is not persisted across tab close or app reload. `test-live-context.mjs` covers context selection, serialized limits and template isolation.
