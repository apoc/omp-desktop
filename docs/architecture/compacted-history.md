# Compacted history (#85)

After a compaction omp's `get_messages` (the agent context) starts at the compaction summary, so a tab opened on a compacted conversation (relaunch, launch restore, resume from history) shows only the post-compaction context. In a tab that was open while it compacted, the live pre-compaction entries stay: `mergeTranscript` keeps entries that have no persisted copy. This feature loads the summarized history back from the session file, read-only, above the current transcript, with a divider per compaction. omp's TUI equivalent is `display.collapseCompacted: false`, a TUI-only setting that has no effect in RPC mode.

## Decisions

- **D1 Source: the session JSONL, read in Rust.** New command `session_history` (module `src-tauri/src/session_history/`). The webview never gets raw entries: the command returns only what the transcript renders. omp's `get_entries` is not used. It returns every entry, including tens of MiB of tool results, through the RPC pipe, the event journal (`replay_events`) and the webview.
- **D2 Confinement.** `session_file` must pass the same check as `conversation_tree` (`conversation_tree::validate`: a `.jsonl` file under the profile's sessions root, symlink escape refused). The profile is resolved through `ProfileStore::resolve_owned` (the `conversation_tree` command shape), and the work runs off the IPC thread (`off_ipc`). A file omp has not written yet returns an empty result.
- **D3 Path.** The current branch is the ancestor chain (`parentId`) of omp's leaf, resolved the way omp resolves it on load (`resolveSessionLeafId`). Take the last entry's `activeLeafId`, or its `id` when `activeLeafId` is absent. A `null` `activeLeafId` means no leaf: the result is empty. An `activeLeafId` that names no entry falls back to the newest entry whose own leaf is itself. Entries off the path (other branches) are never returned. The path walk stops at an id it has already seen, which guards against cycles.
- **D4 Anchor and paging.** Arguments: `sessionFile`, `profile`, `before` (optional number) and `limit` (u32, clamped to 1..=500).
  - `before` is omp's message `timestamp` (ms) of the oldest user/assistant entry with a `ts` the tab shows. The anchor is the last path entry whose `message.timestamp` equals it. The result covers the display-sequence items before the anchor (D5 order, so a divider placed right before the anchor entry is included): after a compaction that kept a tail, the tab anchors on the first kept entry and its divider comes back with the page.
  - With no `before`, the result covers the whole path.
  - When `before` matches no path entry, the result is `{ items: [], more: false }`.
  - The result is the newest `limit` *display items* of that range, in path order. `more` says whether an older display item exists before the returned slice. Non-counted items (`custom`, assistants that aren't display items) are returned only when they sit inside the slice.
  - Unless the slice reaches the path's beginning, it starts at a counted, visible user/assistant item (a user message, or an assistant with non-blank text or thinking) with a numeric `timestamp`, since the frontend anchors the next `before` on the oldest such item it renders: dividers, custom items and error-only assistants (a retried one renders nothing) ahead of the first such item go to the next page, and a slice holding none extends back to the nearest one before it (so a page may exceed `limit`) — each item is returned exactly once.
  - Two passes keep a request cheap on files of tens of MiB: the first records per entry only its links, `message.timestamp`, display facts and line offset; after the window is known, only the window's lines are read again to build the items. omp appends while it runs, which leaves the offsets valid. When a re-read line no longer holds its entry (omp rewrote the file in place), the command fails with an error rather than return wrong data; the frontend shows it and the user retries.
- **D5 Items (the wire contract).** Items are shaped like omp `AgentMessage`s so the frontend reuses `adaptAgentMessages` (and its `finalFailures`) unchanged. For `message` entries `timestamp` is the message's own numeric timestamp. `custom_message` and `compaction` entries have none, so theirs is the entry's ISO timestamp converted to epoch ms (omitted when it is not omp's `toISOString` format).
  - `message` entry with role `user` → `{ role: "user", timestamp, content }`. `content` keeps only `text` and `image` blocks; a string content becomes one text block. A user message with no non-blank text and no image is dropped, not counted.
  - Images: omp persists image data of 1 KiB and more as `blob:sha256:<hex>` references to `<agent dir>/blobs/<hex>` (the `sessions` directory's sibling, omp's `getBlobsDir`). The command resolves them for the returned page only, to the blob's base64. A reference is resolved only when its suffix is exactly 64 lowercase hex chars (omp's `parseBlobRef`) and the canonical blob path stays inside the canonical blobs directory; one blob is read up to 10 MiB, a page up to 32 MiB of blobs. A reference that is malformed, missing, unreadable, escaping or over a cap drops its block. A user message whose only image carries a malformed reference is not shown or counted. One left with no text and no image because its blob could not be read is dropped too, but only after the window was cut, so that page holds one display item fewer.
  - `message` entry with role `assistant` → `{ role: "assistant", timestamp, content, stopReason, errorMessage, errorStatus, provider, model, usage, retryRecovery }`. `content` keeps only `text` and `thinking` blocks; absent fields are omitted. Always returned, because `finalFailures` needs the assistant sequence. It counts as a display item only when it has non-blank text or thinking, or `stopReason === "error"`. Blank is judged on the raw JSON string: whitespace and the escapes `\n`, `\t`, `\r`, `\f` are blank; any other escape (`\u0020` included) counts as visible.
  - `custom_message` entry → `{ role: "custom", customType, timestamp }` (no content). Returned for `finalFailures` boundaries, never counted.
  - `compaction` entry → `{ role: "compactionSummary", timestamp, summary, shortSummary, tokensBefore }`, counted. **Placement:** the item sits immediately before the path entry whose id is its `firstKeptEntryId`, so everything above the divider is what that compaction summarized. When `firstKeptEntryId` is empty or not an earlier path entry, it sits at the compaction's own position.
  - Snapcompact rescue: a `snapcompact` compaction followed on the path by a `snapcompact` compaction whose `parentId` is its id, with the same `firstKeptEntryId` and `tokensBefore`, is skipped (omp's transcript rule).
  - Everything else (tool results, `branch_summary`, model/label/usage entries, …) is not returned. Malformed lines are skipped, as in `conversation_tree/parse.rs`.
- **D6 Frontend state.** Each tab has `olderHistory: { available, loading, error }` in live state (`live.js` `state.olderHistory`, `NO_OLDER_HISTORY` when fresh or after `/new`). It goes through snapshot and restore like `trimmed`, and `loading` is restored as `false`. The bridge snapshot carries it as `olderHistory`, with the cap as `transcriptMax`.
  - Each `get_messages` asks `OMP_OLDER_HISTORY.isAvailable(rawMessages, merged, { trimmed })` (`app/older-history.js`). It is false when `state.trimmed` is set or the raw context's first message is not a `compactionSummary`. Otherwise it looks at the merged transcript's oldest user/assistant entry with a `ts`:
    - none: true — nothing on screen has a `ts`, so the whole path is older (the load sends `before: null`);
    - a loaded entry (`fromHistory`): null, and `available` keeps its value. The last load's `more` still says whether older history exists, so a tab switch (whose `get_messages` finds loaded history on top) does not end paging;
    - otherwise: true when the context returned that entry's message; null when it did not. A live entry the context no longer holds predates a compaction, and the verdict stands: a tab whose first `get_messages` had no leading summary stays false (the history is already on screen), and a compacted tab whose context a later compaction cut again stays true (nothing older was loaded).
  - A load sets `available` from its result (D7).
  - `_trimMessages` sets `available` to false when it cuts the head: loading the cut history back would undo the cap.
  - `room` = `MINIMAP_MAX` − transcript length (`OMP_OLDER_HISTORY.room`). The cap stays: loaded entries count toward it, and `_trimMessages` may later cut them like any other head.
- **D7 Loading.** `OMP_BRIDGE.loadOlderHistory()` (`live.js` `_loadOlderHistory`) invokes `session_history` with the tab's registry `sessionFile` and profile (`_activeProfileId()`), `before` = `OMP_OLDER_HISTORY.anchorTs` (the oldest shown user/assistant `ts`, null when none) and `limit` = room. A tab with no `sessionFile` gets the error `NO_SESSION_FILE` and nothing is invoked; with no room, or a load already running, nothing happens. This is a Tauri command, not an RPC command: `ALLOWED_COMMAND_TYPES` is not involved.
  - `OMP_OLDER_HISTORY.adaptHistory(items, { next })`: the messages between dividers go through `adaptAgentMessages`, and `compactionSummary` → `{ kind: "compact", status: "done", shortSummary, summary, tokensBefore }` (the existing `CompactRow`). Whether a failed reply ended its run is judged over the whole loaded sequence, as `finalFailures` over the uncut list would: a divider is not a run boundary (omp compacts on overflow and continues the reply). Each segment is adapted together with everything after it and keeps only its own share; an entry's output depends only on the messages after it, so `adaptAgentMessages` stays unchanged. `next` is the kind of the oldest message the transcript shows (`oldestMessage(state.messages)?.kind`, passed by `_loadOlderHistory`). When it is `"assistant"`, that reply continues the page's tail run, so a failed reply at the page's end did not end it: an empty assistant message (it renders nothing and adds no entry) is appended to the page while adapting, which makes the tail's failure non-final. With a user message (or nothing) on top the failure is shown. Every loaded entry, divider included, carries `fromHistory: true`.
  - The result applies only if the same tab is still active, with no tab switch (`_switchGen`), conversation reset (`sessionContext`) or session-file change in between, and its anchor is unchanged. Otherwise it is dropped and `loading` is cleared (in the tab's snapshot when it is in the background). Only a tab's newest load writes: a load dropped after a newer one started leaves that one's state alone.
  - `OMP_OLDER_HISTORY.prepend` recomputes room at apply time and puts in the newest entries that fit. When the cap cuts, or Rust reports `more` for the page (`prepend(…, { more })`), entries without a `ts` (dividers) that would be the oldest kept are left out too and counted in `cut`: the next load anchors on the first message after them, and Rust would return them again. A page can start with a divider after adapting even though it is uncut, for instance when its first display item is a continued failed reply the adapter drops. Only a page that starts at the beginning of the path (`more: false`, uncut) keeps a leading divider. `available` becomes `added > 0 && (cut > 0 || more)`: true while the cap cut some of the page or Rust reports more, false after `more: false`, and false for a page that added nothing (the anchor would not move, so asking again returns the same). A failed invoke keeps `available` and sets `error` to Rust's reason.
  - Prepending shifts index-keyed live state (`activeToolCards`) by the number added, the mirror of `_trimMessages`. `notify` stamps the new entries' `_id`s.
  - Loaded entries carry their `ts` and have no copy in the context, so the next `mergeTranscript` keeps them in place. Divider rows carry no `ts`.
- **D8 UI.** While `OMP_OLDER_HISTORY.showRow(olderHistory, messages, max)` holds — `available && room > 0` (`chat-view.jsx`) — `chat/earlier-history-row.jsx` sits at the top of the chat: "Earlier history was compacted" with a "Show earlier history" button. The button reads "Loading…" (disabled) while loading; on an error it reads "Retry" and the row shows "Could not load earlier history: {reason}" (`OMP_OLDER_HISTORY.reasonOf(error)`: Rust's text as is, shown untranslated; `NO_SESSION_FILE` as the source string "omp has not saved this conversation yet", which the row passes to `OMP_TR`). Strings go through `OMP_TR` (`app/i18n-zh.js`).
- **D9 Setting.** Settings → Session → Tabs: "Show compacted history" (tweak `showCompactedHistory`, default off; listed in `OMP_SESSION_PREFS` KEYS). When it is on, a `get_messages` whose `isAvailable` is true starts one load by itself; after it the oldest shown message is loaded history (`isAvailable` null), so later `get_messages` do not load again. The row and the button work with the setting off.
- **D10 Scope.** `get_messages` keeps dropping omp's leading `compactionSummary` message: rendering it there would need a merge key against the live `/compact` row, whose response carries no timestamp. The divider comes only from loaded history. Remote (phone) views show whatever the transcript holds. No change to the 169-entry cap. omp's version floor is unchanged: no new RPC.
