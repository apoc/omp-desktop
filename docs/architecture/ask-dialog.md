# Ask dialog

Once `set_ask_dialog {enabled: true}` is on, omp's ask tool reaches the desktop as one `extension_ui_request` with `method: "ask"` carrying every question of the call (`header`, options with `description`/`preview`, `multi`, `recommended`, an optional `timeout`). The flag is off by default and per process, so `_initFetch` sends it on every activation, like the subagent subscription; without it omp falls back to one `select` per question (plus an `editor` for typed text), which still works as plain prompts. `app/ask-dialog.js` (`window.OMP_ASK_DIALOG`, regression `test-ask-dialog.mjs`) holds the rules, `chat/ask-dialog.jsx` renders the card inside the ask bubble.

## HTML forms (omp 19.1+)

Since omp 19.1.0 the ask tool's `questions` shape is replaced by one HTML `<form>`: `{type: "extension_ui_request", id, method: "form", html: "<form>…</form>", timeout?}`. There is no opt-in flag and no per-field fallback for that release. The reply is `{type: "extension_ui_response", id, data: {<control name>: value}}`: one string for a radio or single select, an array for a checkbox group or multiple select, a number for a `number`/`range` input, and a group's free-text Other as the lone unmatched string (or the last array entry). `{cancelled: true}` closes it.

- `app/html-form-markup.js` and `app/html-form-parse.js` (`window.OMP_HTML_FORM_MARKUP` and `window.OMP_HTML_FORM_PARSE`, regression `test-html-form.mjs`) port omp v19.2.1's own markup parser (its tokenizer, entity table, optional end tags, no HTML5 tree construction) and its form builder (`tools/html-form/parse.ts`), so the desktop sees exactly omp's fields, labels and option values; `tests/fixtures/html-form-omp-corpus.json` (generated from omp's sources) checks this. The HTML never enters the DOM. As in omp, the form is the first `<form>` (the whole document when there is none) and content outside it is ignored. The builder keeps omp's rules: sections from `<fieldset>`/`<legend>` and loose content, text/list/pre/table context (including decision-matrix column labels), labels (`for`, wrapping, `aria-label`, name fallback), radio groups by name, checkbox groups, select/multiple, text-like inputs, textarea, hidden inputs, disabled options, checked/selected defaults and `required`/`min`/`max`/`minlength`/`maxlength`/`pattern` hints. Multiline option whitespace follows omp's `parse.ts`. Missing radio/checkbox values are `"on"`; later enabled duplicate values are disabled to prevent ambiguous submissions. A radio or checkbox group of two or more options without an option labelled "Other…" gets an automatic Other text box (including a group whose borrowed column label is "Other"). Only text, alt text and control values reach the React tree: the HTML string is never injected, and a picture is shown as its alt text, never its source URL. Limits, each refusal naming its reason and cancelling the request: HTML over 256 KiB (UTF-8 bytes) is refused before parsing; the whole document is bounded to 10,000 nodes (`<head>` included), 64 open elements and 4 MiB of start-tag scanning; a form is bounded to 500 fields, 1,000 options (select and radio/checkbox), 2,000 blocks, 2,000 table cells and 64 KiB of text shown (UTF-8 bytes of every label, option, value, placeholder and text block).
- Password forms are refused with a terminal-only note. `reader.rs` applies its rule in `sanitize_logical` to every logical frame: a single line and a reassembled protocol-v2 `rpc_chunk` run alike. A line that does not parse becomes a fixed `desktop_frame_error` frame, so its text never passes through. For an `extension_ui_request` with `method: "form"` and a string `html`, the rule decodes character references before searching: numeric decimal and hex references, with or without `;`, and the named references it knows (`amp`, `lt`, `gt`, `quot`, `apos`, `nbsp`, `Tab`, `NewLine`, `fjlig`, and the uppercase `AMP`, `LT`, `GT`, `QUOT`). A bare `&` or an unknown reference is kept as literal text (no named reference decodes to an ASCII letter of "password"), then the decoded text is searched for `password`, ASCII-case-insensitively. Any match replaces `html` with the fixed marker `<form data-omp-desktop-redacted="password"></form>` before that frame is journaled or emitted, so neither the original markup nor a prefilled value reaches the event log, its replay or the webview. `html-form-parse.js` refuses a form whose root carries that marker, or any `input` whose `type` or `autocomplete` contains "password" (case-insensitive), with the same note. The rule protects the form request frame only: the ask tool's own call arguments (`tool_execution_start.args.html`, and the `toolCall` arguments in `message_update` / `message_end`) carry the same model-written HTML and are not rewritten, and omp also stores it in its session file. **Known limitation:** the match covers the whole decoded text, so a form that merely mentions "password" (in a field name, a label or prose) is refused too; that is the deliberate fail-closed trade-off.
- `OMP_HTML_FORM.emptyDraft`/`pick`/`setOther`/`setText`/`clearPick` are the draft rules (picking a radio clears its Other text; choosing "Choose…" again clears a single-select's pick). `buildData` is the only reply builder. `draftErrors` checks each field against its own draft entry (omp's shape rules, then `fieldError`, then whether a same-name field replaces its answer). `answerError` (shape, then `fieldError` on every field's value as omp reads it) validates an untrusted phone answer and gates `answerForm`; `dataError` is its shape-only half. omp rejects unknown names, wrong shapes, duplicate entries and disabled options. omp 19.1's field rules (`fieldError` in its `data.ts`: `required`, number `min`/`max`, `minlength`/`maxlength`, `email`, `url`) block Submit on every omp version. `pattern` is a hint only and never runs client-side: a model-written regex in the webview would be a ReDoS risk, so the desktop shows it and does not enforce it. On omp 19.1.x a pattern mismatch makes omp fail the ask tool, which the desktop cannot see; `step` is checked by neither version. Submit also stays disabled for an Other text equal to a disabled option, and for a field whose answer a same-name field replaces. A refusal from `answerForm` shows on the card as `formError`, and nothing reaches omp. Errors are `{text, vars}` objects: the desktop translates them with `OMP_TR`, and the phone fills them in with `OMP_HTML_FORM.errorText`. `answerForm` merges the desktop's parsed hidden values back into the outgoing response; phone answers omit them.
- A request that cannot be parsed or exceeds the parser limits is cancelled at once and leaves a bubble with the reason, so omp never waits. A failed answer or cancellation hand-off is visible and reopens the prompt for another delivery attempt. An unsupported form's reopened bubble shows a Retry control that resends the cancellation. The reopened bubble keeps its parse error (`formError`) and carries the failure separately as `deliveryError`, which a retry clears as it settles and an omp withdrawal clears too. An omp withdrawal still wins: it keeps the bubble closed and clears any undelivered answer data. The bubble uses the ask look: `chat/form-dialog.jsx` renders sections and rows, a native select for a single-choice select, inputs and textareas, Submit/Cancel, field errors and a timeout chip ("omp submits the form's defaults after …"). Text-like inputs use `OMP_HTML_FORM.inputType` on the desktop and the phone: the browser's own type only when it keeps the field's default unchanged (a range input shows its midpoint for an empty value, a date input nothing for an unreadable date), otherwise `text`, so what the field shows is what omp receives. A cancelled or omp-withdrawn form shows one status row (`closed by omp` or `cancelled`) instead of its field list. Answered and cancelled forms collapse like every ask; the summary omits hidden inputs.
- Timeout is omp's: it withdraws the request (`cancel`) and submits the form's defaults. The chip says so. omp's timeout sends the same `cancel` frame as a stopped turn, so the card cannot tell them apart and both read `closed by omp`. If the defaults break a field's rules (an empty required field, for example), omp reports the ask as timed out before the user answered its required fields and gives no answer.
- Both paths stay supported: omp below 19.1 still sends per-field `select`/`input`/`editor` prompts, so `MIN_OMP_VERSION` does not move.

The rest of this file describes the `ask`, `select` and approval paths.

- The reply is `answers: [{id, selectedOptions, customInput?}]` (`OMP_BRIDGE.answerAskDialog`). omp validates it and fails the ask tool on any mismatch (rpc-mode.ts `parseAskDialogResponse`): one answer per question in request order, exact labels, and a pick-one question carries one option *or* typed text. `answers()` builds only that shape; the regression replays random clicks and typing against a port of omp's checks. A request the dialog cannot parse is cancelled, so omp never waits on it.
- The request reaches stdout *before* its ask tool's `tool_execution_start` (seen live), like a tool-approval `select`, so it goes through `_queueAskBubble` too; pushed on arrival it sits above its own tool card.
- A lone pick-one question with options answers on click; anything else sends on Submit, which waits until every pick-one question has an option or typed text (pick-any may stay empty). A lone pick-one question answered with nothing would read as a cancel in omp.
- Cancel sends `cancelled: true`, which makes omp abort the turn — as Esc does on omp's own dialog; Esc here keeps its window meaning (stop the turn). omp's `cancel` frame (turn stopped, or its `ask.timeout` ran out and it picked the recommended options itself) marks the bubble `closedByOmp`.
- Over RPC an answer has no note, no images and no "chat about this": the reply carries only `selectedOptions` and `customInput`.
- Picks not sent yet live in `ask-dialog.jsx`'s module map keyed by request id: the chat view remounts on a tab switch. Shift+Tab is stopped at the dialog so it moves focus instead of cycling the thinking level.
- `select` stays for tool approvals and extension pickers (`/review`), without a free-text box: those callers expect one of their own options. Since omp 18.18.3 it also carries the ask tool's HTML-form choice fields: an RPC host has no `formDialog`, so omp asks a form one field at a time (`tools/ask.ts` `askFieldByField`: choice fields through `select`, text fields through `input`/`editor`).
- A `select` renders as full-width rows in the ask-dialog card (`.ask-dialog` › `.ask-q` › `.ask-rows`), on the desktop (`chat/ask-bubble.jsx`) and the phone (`src/remote/transcript.js`); a click answers at once with the option's label. Once a desktop ask bubble is answered or cancelled it collapses to a one-line summary: the answer (or existing cancellation/`closed by omp` status, which also covers omp-side timeout), the prompt's first line and its time. The summary is a keyboard-accessible button with `aria-expanded`; clicking it reveals the full settled card, and clicking again collapses it. Expansion is per-bubble React state, is not persisted, and resets when a visible prompt settles. The phone still drops a card once answered. One pure rule, `OMP_ASK_DIALOG.selectRows(msg)` (`app/ask-dialog.js`, regression `test-ask-dialog.mjs`, also served to the phone as `/ask-dialog.js`), turns the request into rows from omp's optional `selectionMarker` (`"radio" | "checkbox"`), `checkedIndices` and `markableCount` (sent on RPC since omp 18.20.0, the `MIN_OMP_VERSION` floor; `live.js` and `app/remote-view.js` `askCard` copy them through, `selectRows` validates them):
  - no marker (tool approvals, extension pickers): every row gets a radio mark (`markableCount` is ignored), the group is a `radiogroup`, and a row is checked only once it is the bubble's answer;
  - `"radio"` (single-choice form fields): as with no marker, except that only the first `markableCount` rows (default: all) get the radio mark; later rows are actions with no mark and no checked state (omp's wire meaning: the marker covers the first `markableCount` options, trailing ones are actions);
  - `"checkbox"` (checkbox groups and multi-selects, which omp asks again after every toggle with a `(N selected)` title prefix): the first `markableCount` rows (default: all) get a box mark, checked exactly when their index is in `checkedIndices` (omp's state, authoritative, also for the row the bubble was answered with); later rows are actions (`✔ Done selecting`) with no mark and no checked state; the group is a plain `group`;
  - a row with a mark is `role="radio"`/`"checkbox"` with a boolean `aria-checked`; an action row is a plain button. The checked state drives the `.ask-row.checked` class (filled mark; a box's tick is the desktop's check icon, or a CSS tick in `ask.css` where the mark is empty, as on the phone); on the desktop `.selected` still highlights the picked row of an answered bubble and the others are `.dimmed`. A select's `.ask-q` section carries `ask-select` on both sides, so the ask dialog's `.selected` mark fill skips it. The phone drops a card once answered, so it never shows a picked row.
- Tool approvals are that `select` with options exactly `["Approve","Deny"]` and a title `Allow tool: <name>` plus detail lines (omp `formatApprovalPrompt`: optional `Origin:`/`Reason:`, then the tool's `formatApprovalDetails()` — command, path, content preview). `app/approval.js` (`OMP_APPROVAL.approvalInfo`, regression `test-approval.mjs`) splits head from details and mirrors Rust's `approval::approval_tool_name` grammar, which decides whether the "allow for this session / project" buttons appear. A prompt an approval rule covers never reaches the frontend: `reader.rs` `try_auto_approve` answers it on omp's stdin and forwards `{type: "desktop_auto_approval", tool, details}` (`details` = the title after its first line, or `null`). `live.js` turns that into a desktop-made `kind: "approval"` row (`autoApprovalRow`, no `ts`) queued through `_queueAskBubble`, so it lands after its tool card like a manual prompt; `chat/approval-row.jsx` shows the tool and the first detail line that is not `Origin:`/`Reason:`, with the full details (plain text, never markdown) unfolding on click (#42). The frame carries no `toolCallId`, so the row is never merged into a card: with parallel calls a name match would be a guess.
- A standing grant ("allow for this session / project") is bound to the prompt, not to the active tab, and is made together with the prompt's "Approve" answer in one IPC call. The bubble carries its `sessionId` (the tab whose frames built it: `_switchToSession`'s listeners, and every step after an await, stop once their activation is superseded or detached) and its request `id`, and `approval_approve_and_grant` takes only those two plus the scope. Rust (`AgentBridge::approve_and_grant`, `agent/approvals.rs`) looks the prompt up among the ones that session's live process forwarded and that are still unanswered — the stdout reader records every approval prompt it did not auto-answer (ids up to 256 bytes); omp's `cancel`, an `extension_ui_response` for that id written by `AgentBridge::send`, and this call each remove it; at most 64 per process (the oldest goes), gone with the process. Under the `sessions` lock it takes that prompt together with the same entry's stdin, so the answer can only reach the process incarnation that asked; no running process, no such prompt — one shown in the wrong tab, one from a process restarted under the same id, one already answered or granted, one evicted or never recorded — or a project grant for a process with no folder, and the call is rejected with nothing written and nothing saved. It then writes `{type: "extension_ui_response", id, value: "Approve"}` to that stdin, and only once that write succeeded grants the prompt's tool (under that process's own folder for project scope); a failed write puts the prompt back, saves no rule and is a rejection too. Answer-then-grant rather than grant-then-roll-back: a rollback could revoke a rule the user already had, and a rule saved first would auto-answer the process's other prompts while this one is still open. The session-scope insert runs under the bridge lock and only if the entry is still the incarnation the prompt came from, so it cannot outlive a reap that already cleared the session's grants. The command resolves to `null` (answered and granted) or a reason string (answered, rule not saved — the rules file failed, or the process was replaced right after the answer); a rejection always means omp got nothing. The buttons call `OMP_BRIDGE.approveAndRemember`, which settles the bubble at once (no second click can race the call) and then makes that one call for the prompt's own session, whichever tab is active by then. On a rejection it reopens that exact bubble (`_reopenAsk`) for a plain Approve/Deny and adds a note — never a fallback `send_command` Approve, which could answer a respawned process; on a reason string it adds an "approved, but the rule was not saved" note. Both outcomes land in the prompt's own tab: the live transcript when that tab is shown, its saved snapshot otherwise, so a tab switch during the call (including one still in its listener teardown) does not lose them. An omp withdrawal (`closedByOmp`) that arrived meanwhile wins: the bubble stays closed and gets no "open again" note. Revoke and list still act on the active tab: they only narrow or read.
