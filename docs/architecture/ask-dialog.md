# Ask dialog

Once `set_ask_dialog {enabled: true}` is on, omp's ask tool reaches the desktop as one `extension_ui_request` with `method: "ask"` carrying every question of the call (`header`, options with `description`/`preview`, `multi`, `recommended`, an optional `timeout`). The flag is off by default and per process, so `_initFetch` sends it on every activation, like the subagent subscription; without it omp falls back to one `select` per question (plus an `editor` for typed text), which still works as plain prompts. `app/ask-dialog.js` (`window.OMP_ASK_DIALOG`, regression `test-ask-dialog.mjs`) holds the rules, `chat/ask-dialog.jsx` renders the card inside the ask bubble.

- The reply is `answers: [{id, selectedOptions, customInput?}]` (`OMP_BRIDGE.answerAskDialog`). omp validates it and fails the ask tool on a mismatch (`parseAskDialogResponse`): one answer per question in request order, exact labels, and a pick-one question carries one option *or* typed text. `answers()` builds only that shape. A request the dialog cannot parse is reported visibly and sent without answers, so native validation fails the tool rather than mistaking a desktop compatibility failure for a user cancellation and aborting the turn.
- The request reaches stdout *before* its ask tool's `tool_execution_start` (seen live), like a tool-approval `select`, so it goes through `_queueAskBubble` too; pushed on arrival it sits above its own tool card.
- A lone pick-one question with options answers on click; anything else sends on Submit, which waits until every pick-one question has an option or typed text (pick-any may stay empty). A lone pick-one question answered with nothing would read as a cancel in omp.
- Cancel sends `cancelled: true`, which makes omp abort the turn — as Esc does on omp's own dialog. Escape also invokes Desktop's global interrupt while streaming unless another overlay handles it. Native `cancel` frames identify the request but carry no reason: signal abort and timeout use the same frame. On timeout native chooses each question's recommended option, or its first option when none was recommended. Desktop shows a closed outcome without attributing a particular cause.
- Over RPC an answer has no note, no images and no "chat about this": the reply carries only `selectedOptions` and `customInput`.
- Picks not sent yet live in `ask-dialog.jsx`'s module map keyed by request id: the chat view remounts on a tab switch. Shift+Tab is stopped at the dialog so it moves focus instead of cycling the thinking level.
- `select` stays for tool approvals and extension pickers (`/review`), without a free-text box: those callers expect one of their own options.
- Tool approvals are that `select` with options exactly `["Approve","Deny"]` and a title `Allow tool: <name>` plus detail lines (omp `formatApprovalPrompt`: optional `Origin:`/`Reason:`, then the tool's `formatApprovalDetails()` — command, path, content preview). `app/approval.js` (`OMP_APPROVAL.approvalInfo`, regression `test-approval.mjs`) splits head from details and mirrors Rust's `approval::approval_tool_name` grammar, which decides whether the "allow for this session / project" buttons appear. A prompt an approval rule covers never reaches the frontend: `reader.rs` `try_auto_approve` answers it on omp's stdin and forwards `{type: "desktop_auto_approval", tool, details}` (`details` = the title after its first line, or `null`). `live.js` turns that into a desktop-made `kind: "approval"` row (`autoApprovalRow`, no `ts`) queued through `_queueAskBubble`, so it lands after its tool card like a manual prompt; `chat/approval-row.jsx` shows the tool and the first detail line that is not `Origin:`/`Reason:`, with the full details (plain text, never markdown) unfolding on click (#42). The frame carries no `toolCallId`, so the row is never merged into a card: with parallel calls a name match would be a guess.
- A standing grant ("allow for this session / project") is bound to the prompt, not to the active tab. The bubble carries its `sessionId` and request `id`; `approval_approve_and_grant` takes those plus the scope. Rust (`AgentBridge::approve_and_grant`, `agent/approvals.rs`) claims an unanswered approval and the same process's stdin together. The approval registry holds at most 64 prompts with IDs up to 256 bytes; cancellation, an answer or process exit revokes a claim. A missing prompt or project folder is refused. Rust writes the approval first and saves the tool rule only after the write, under that process's own project when applicable; a failed write saves nothing and does not restore a cancelled claim. A session grant is made only while the same process incarnation is registered. The result is `null` for answered and granted, a reason string for answered but not saved, or an error when the answer was not written. `OMP_BRIDGE.approveAndRemember` uses the same in-flight guard and tab-scoped completion as ordinary answers. A rejection leaves the still-live prompt open with its error; a native cancellation or process exit wins the race. There is never a fallback approval send to a potentially different process. Revoke and list narrow or read rules for the active tab.

## Live question lifecycle

Live callbacks belong to one process and tab. A buffered request is flushed before leaving its tab; native cancellation closes only the named request, including before that flush. An unanswered question is retained through transcript trimming even if another tool causes a turn boundary; the 13 most recent cancelled outcomes are retained too. Pending controls stay open during an answer write, block duplicate sends, and retain their draft and a visible error if Rust rejects the write. A successful write means the frame reached the process pipe, not that omp returned an acknowledgement. A later native cancellation or process exit closes the callback instead of reopening it from a delayed write result. Process exit is shown separately from an unspecified native cancellation.

The per-process journal keeps a bounded snapshot of unanswered request frames alongside its event ring. On activation the frontend applies replay events first, reconciles the snapshot at that replay head, and then drains later live events. The snapshot can recover a live question whose original event fell out of the ring; an authoritative absence closes a previously shown callback as no longer pending, without claiming whether it was answered elsewhere or cancelled. A locally answered request is not resurrected by an older snapshot. Neither the journal nor its snapshot survives process replacement or app restart.

The snapshot retains at most 64 requests, request IDs up to 256 UTF-8 bytes and 8 MiB of redacted frame bytes per process. Overflow, unsupported methods or discarded oversized frames make it incomplete until process replacement; an in-flight response also makes it temporarily incomplete. Absence from an incomplete snapshot is not authoritative. If the event ring also dropped events the transcript warns that questions may be missing. Rust rejects an unknown response ID only while the snapshot is complete; otherwise an untracked live request must still be answerable. Auto-approved prompts never enter this snapshot.

Protocol-v2 chunked questions use the existing bounded native frame decoder, not a second reassembly buffer. The pending snapshot retains a redacted logical request at its final physical sequence number, while normal event replay still forwards the original chunks. This keeps large questions answerable after their physical frames leave the ring; decoded requests beyond the snapshot byte budget make its membership incomplete rather than rejecting their responses.

## Persistent input reminder

`OMP_PENDING_INPUT` selects unresolved requests independently of the strongest run state. `PendingInput` stays in the composer, outside the scrolling transcript and independent of Ambient visibility; it counts all questions and lets the user choose among parallel requests. Sending and failed-delivery requests remain pending. The main empty-draft action is **Answer**, not just the stop square. The stop control names its question-cancellation effect.

A reminder click identifies the current request by id. Chat explicitly unpins follow-output, scrolls to the card and focuses an enabled control. Other updates do not steal focus or pull the view away from the question. Concurrent work is derived from identified background jobs/subagents and the native pending-work aggregate, never from `isStreaming` alone: an ask blocks inside a live turn. The header makes input waiting and other active work visible together. Regression rules live in `test-pending-input.mjs`; delivery and replay behavior is exercised through the public bridge in `test-ask-recovery.mjs`.

## Questions across app restarts

Unanswered **ask-tool questions** reappear when a saved conversation is resumed or reopened on launch. The restored card preserves the questions, choices, descriptions, previews, multi-select rules and recommended options. Parallel unanswered asks form one dialog so submitting one answer cannot strand the rest. Unsaved partial picks are still memory-only.

The bridge reads native `get_entries` after protocol negotiation. `get_messages` is provider-filtered and can omit the unfinished assistant tool call entirely, so it cannot be the recovery source. `OMP_ASK_RECOVERY.fromEntries` walks backward from the returned `leafId`; missing parents, cycles, duplicate ids and malformed questions fail closed. Only the current unanswered batch qualifies. Answered asks, explicit cancellations/aborts, a later user reply or completed assistant turn, and abandoned branches do not reopen. Native process-exit diagnostic results are not user answers. State/history reply order is immaterial; tab switches, conversation changes and new user/live-question events invalidate stale recovery requests.

Recovery never replays tools, invokes a model, reissues an approval or sends the dead process's request id. The card is labelled **restored**. Submitting validates the answer and sends the question/answer pairs as a normal user `prompt` to that conversation's current process, which continues from the reply. Slashes and angle brackets in the JSON data are escaped so quoted skill tokens and harness tags cannot dispatch commands. Live questions still use their original `extension_ui_response` callback. A rejected send leaves the restored card open with its error; in-flight controls cannot double-submit.

**Cancel** does not wake the agent. It stores the dismissed tool-call ids in local app storage under `omp-desktop:ask-dismissed:<conversation file>`, scoped by the full conversation path (and therefore its profile), so another launch does not restore a deliberately dismissed question. A failed storage write leaves it open with an error. Tool approvals and extension/OAuth pickers are not reconstructed: their dead execution context must never be treated as an active grant or callback.

`test-ask-recovery.mjs` exercises the public bridge against native-shaped filtered messages and raw entries, including branch isolation, grouped asks, cancellation persistence, refusal, live callbacks, command-token inertness and response ordering. The native smoke uses an isolated real omp process with a loopback-only model endpoint: the restored answer is persisted and remains settled after another process restart. The actual AskBubble/AskDialog controls are also exercised in Chromium against that native RPC process.
