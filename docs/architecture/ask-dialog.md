# Ask dialog

Once `set_ask_dialog {enabled: true}` is on, omp's ask tool reaches the desktop as one `extension_ui_request` with `method: "ask"` carrying every question of the call (`header`, options with `description`/`preview`, `multi`, `recommended`, an optional `timeout`). The flag is off by default and per process, so `_initFetch` sends it on every activation, like the subagent subscription; without it omp falls back to one `select` per question (plus an `editor` for typed text), which still works as plain prompts. `app/ask-dialog.js` (`window.OMP_ASK_DIALOG`, regression `test-ask-dialog.mjs`) holds the rules, `chat/ask-dialog.jsx` renders the card inside the ask bubble.

## HTML forms (omp 19.1+)

Since omp 19.1.0 the ask tool's `questions` shape is replaced by one HTML `<form>`: `{type: "extension_ui_request", id, method: "form", html: "<form>…</form>", timeout?}`. There is no opt-in flag and no per-field fallback for that release. The reply is `{type: "extension_ui_response", id, data: {<control name>: value}}`: one string for a radio or single select, an array for a checkbox group or multiple select, a number for a `number`/`range` input, and a group's free-text Other as the lone unmatched string (or the last array entry). `{cancelled: true}` closes it.

- `app/html-form.js` (`window.OMP_HTML_FORM`, regression `test-html-form.mjs`) parses the HTML with `DOMParser` and mirrors `tools/html-form/{parse,data}.ts`: sections from `<fieldset>`/`<legend>` and loose content, text/list/pre/table context (including decision-matrix column labels), labels (`for`, wrapping, `aria-label`, name fallback), radio groups by name, checkbox groups, select/multiple, text-like inputs, textarea, hidden inputs, disabled options, checked/selected defaults and `required`/`min`/`max`/`minlength`/`maxlength`/`pattern` hints. HTML is capped at 256 KiB before parsing; total nodes and depth are bounded across the whole document (including `<head>`), while fields and labels come from `<body>`; fields, options, blocks, table cells and the displayed labels (including the field-name fallback for an unlabeled choice group) are also bounded, and excess makes the form unsupported. Multiline option whitespace follows omp's `parse.ts`. Missing radio/checkbox values are `"on"`; later enabled duplicate values are disabled to prevent ambiguous submissions. A radio or checkbox group of two or more options without an option labelled "Other…" gets an automatic Other text box (including a group whose borrowed column label is "Other"). Only text, alt text and control values reach the React tree: the HTML string is never injected. A picture is shown as its alt text, never its source URL.
- Password forms are refused with a terminal-only note. Before a form request is journaled or emitted, `reader.rs` decodes its `html` the way a browser decodes character references (numeric decimal/hex with or without `;`, and named references; an unresolved `&` fails closed), ASCII-lowercases the result and searches the whole string for `password`. Any match replaces `html` with the fixed marker `<form data-omp-desktop-redacted="password"></form>`; the original markup and every prefilled value are gone before the desktop's event log or replay can see them. There is no HTML tokenizer and no byte-index slicing, so malformed, unterminated, huge or multibyte input is just a string and cannot panic. `app/html-form.js` refuses a form whose root carries that marker with the same note, and also keeps its structural check on a `type`/`autocomplete` value containing `password` anywhere (decoded, ASCII-case-insensitive). **Known limitation:** because the backend matches the whole decoded HTML, a form that merely mentions "password" — in a field name, a label or prose — is refused as well. That is the deliberate fail-closed trade-off for never leaking a prefilled credential.
- `HTML_FORM.emptyDraft`/`pick`/`setOther`/`setText`/`clearPick` are the draft rules (picking a radio clears its Other text; choosing "Choose…" again clears a single-select's pick). `buildData` is the only reply builder; `draftErrors` checks each field against its own draft entry, and `dataError` (shape) plus `answerError` (shape + the submit rules below) validate untrusted phone input. omp rejects unknown names, wrong shapes, duplicate entries and disabled options. **Submit-time contract per omp version:** 19.1.x's `parseFormDialogResponse` applies `fieldError` (data.ts) to every submitted field's own parsed value — `required`, number `min`/`max`, `minlength`/`maxlength`, `email`, `url` and `pattern` (`^(?:pattern)$`, `v` flag; an invalid pattern is not checked) — and fails the ask tool on a violation, which the desktop never sees beyond the stdin hand-off. 19.2.0+ no longer applies it: there `pattern` is a display hint only, and omp accepts the answer. `step` is checked by neither version. `answerError(form, data, ompVersion)` therefore applies its `fieldError` replay only below 19.2.0, or when the version is unknown; on 19.2.0+ it validates only the shape rules (a required radio sharing its name with a checkbox group is accepted there, as omp accepts it). The draft still shows the 19.1 constraints on every version, never executes a model regex, and refuses any form carrying a `pattern` outright unless the asking tab's omp is 19.2.0+. That version is bound per session: `start_session` returns the `ompVersion` its spawn-time `omp --version` read, and `live.js` stores it on the tab, so two tabs may carry different versions and one tab's rules never use another's omp. An unreadable version counts as too old. Phone submissions omit hidden defaults and `invalidAnswer` uses the asking tab's own version; `answerForm` merges the desktop's parsed hidden values back into the outgoing response and refuses any answer `answerError` rejects.
- A request that cannot be parsed or exceeds the parser limits is cancelled immediately and leaves a bubble with the reason, so omp never waits. A failed answer/cancellation IPC hand-off is visible and reopens the prompt for another delivery attempt, including an unsupported form's refusal, whose reopened bubble shows a Retry control that resends the cancellation. An omp withdrawal still wins: it keeps the bubble closed and clears any undelivered answer data. The bubble uses the ask look: `chat/form-dialog.jsx` renders sections and rows, a native select for a single-choice select, inputs and textareas (number/range keep their input type), Submit/Cancel, field errors and a timeout chip ("omp submits the form's defaults after …"). Answered and cancelled forms collapse like every ask; the summary omits hidden inputs.
- Timeout is omp's: it withdraws the request (`cancel`) and submits the form's defaults. The chip says so.
- Both paths stay supported: omp below 19.1 still sends per-field `select`/`input`/`editor` prompts, so `MIN_OMP_VERSION` does not move.

The rest of this file describes the `ask`, `select` and approval paths.

- The reply is `answers: [{id, selectedOptions, customInput?}]` (`OMP_BRIDGE.answerAskDialog`). omp validates it and fails the ask tool on any mismatch (rpc-mode.ts `parseAskDialogResponse`): one answer per question in request order, exact labels, and a pick-one question carries one option *or* typed text. `answers()` builds only that shape; the regression replays random clicks and typing against a port of omp's checks. A request the dialog cannot parse is cancelled, so omp never waits on it.
- The request reaches stdout *before* its ask tool's `tool_execution_start` (seen live), like a tool-approval `select`, so it goes through `_queueAskBubble` too; pushed on arrival it sits above its own tool card.
- A lone pick-one question with options answers on click; anything else sends on Submit, which waits until every pick-one question has an option or typed text (pick-any may stay empty). A lone pick-one question answered with nothing would read as a cancel in omp.
- Cancel sends `cancelled: true`, which makes omp abort the turn — as Esc does on omp's own dialog; Esc here keeps its window meaning (stop the turn). omp's `cancel` frame (turn stopped, or its `ask.timeout` ran out and it picked the recommended options itself) marks the bubble `closedByOmp`.
- Over RPC an answer has no note, no images and no "chat about this": the reply carries only `selectedOptions` and `customInput`.
- Picks not sent yet live in `ask-dialog.jsx`'s module map keyed by request id: the chat view remounts on a tab switch. Shift+Tab is stopped at the dialog so it moves focus instead of cycling the thinking level.
- `select` stays for tool approvals and extension pickers (`/review`), without a free-text box: those callers expect one of their own options. Since omp 18.18.3 it also carries the ask tool's HTML-form choice fields: an RPC host has no `formDialog`, so omp asks a form one field at a time (`tools/ask.ts` `askFieldByField`: choice fields through `select`, text fields through `input`/`editor`).
- A `select` renders as full-width rows in the ask-dialog card (`.ask-dialog` › `.ask-q` › `.ask-rows`), on the desktop (`chat/ask-bubble.jsx`) and the phone (`src/remote/transcript.js`); a click answers at once with the option's label. Once a desktop ask bubble is answered or cancelled it collapses to a one-line summary: the answer (or existing cancellation/`closed by omp` status, which also covers omp-side timeout), the prompt's first line and its time. The summary is a keyboard-accessible button with `aria-expanded`; clicking it reveals the full settled card, and clicking again collapses it. Expansion is per-bubble React state, is not persisted, and resets when a visible prompt settles. The phone still drops a card once answered. One pure rule, `OMP_ASK_DIALOG.selectRows(msg)` (`app/ask-dialog.js`, regression `test-ask-dialog.mjs`, also served to the phone as `/ask-dialog.js`), turns the request into rows from omp's optional `selectionMarker` (`"radio" | "checkbox"`), `checkedIndices` and `markableCount` (sent on RPC since omp 18.20.0, the `MIN_OMP_VERSION` floor; `live.js` and `app/remote-view.js` `askCard` copy them through, `selectRows` validates them):
  - no marker (tool approvals, extension pickers): every row gets a radio mark (`markableCount` is ignored), the group is a `radiogroup`, and a row is checked only once it is the bubble's answer;
  - `"radio"` (single-choice form fields): as with no marker, except that only the first `markableCount` rows (default: all) get the radio mark; later rows are actions with no mark and no checked state (omp's wire meaning: the marker covers the first `markableCount` options, trailing ones are actions);
  - `"checkbox"` (checkbox groups and multi-selects, which omp asks again after every toggle with a `(N selected)` title prefix): the first `markableCount` rows (default: all) get a box mark, checked exactly when their index is in `checkedIndices` (omp's state, authoritative, also for the row the bubble was answered with); later rows are actions (`✔ Done selecting`) with no mark and no checked state; the group is a plain `group`;
  - a row with a mark is `role="radio"`/`"checkbox"` with a boolean `aria-checked`; an action row is a plain button. The checked state drives the `.ask-row.checked` class (filled mark; a box's tick is the desktop's check icon, or a CSS tick in `ask.css` where the mark is empty, as on the phone); on the desktop `.selected` still highlights the picked row of an answered bubble and the others are `.dimmed`. A select's `.ask-q` section carries `ask-select` on both sides, so the ask dialog's `.selected` mark fill skips it. The phone drops a card once answered, so it never shows a picked row.
- Tool approvals are that `select` with options exactly `["Approve","Deny"]` and a title `Allow tool: <name>` plus detail lines (omp `formatApprovalPrompt`: optional `Origin:`/`Reason:`, then the tool's `formatApprovalDetails()` — command, path, content preview). `app/approval.js` (`OMP_APPROVAL.approvalInfo`, regression `test-approval.mjs`) splits head from details and mirrors Rust's `approval::approval_tool_name` grammar, which decides whether the "allow for this session / project" buttons appear. A prompt an approval rule covers never reaches the frontend: `reader.rs` `try_auto_approve` answers it on omp's stdin and forwards `{type: "desktop_auto_approval", tool, details}` (`details` = the title after its first line, or `null`). `live.js` turns that into a desktop-made `kind: "approval"` row (`autoApprovalRow`, no `ts`) queued through `_queueAskBubble`, so it lands after its tool card like a manual prompt; `chat/approval-row.jsx` shows the tool and the first detail line that is not `Origin:`/`Reason:`, with the full details (plain text, never markdown) unfolding on click (#42). The frame carries no `toolCallId`, so the row is never merged into a card: with parallel calls a name match would be a guess.
- A standing grant ("allow for this session / project") is bound to the prompt, not to the active tab, and is made together with the prompt's "Approve" answer in one IPC call. The bubble carries its `sessionId` (the tab whose frames built it: `_switchToSession`'s listeners, and every step after an await, stop once their activation is superseded or detached) and its request `id`, and `approval_approve_and_grant` takes only those two plus the scope. Rust (`AgentBridge::approve_and_grant`, `agent/approvals.rs`) looks the prompt up among the ones that session's live process forwarded and that are still unanswered — the stdout reader records every approval prompt it did not auto-answer (ids up to 256 bytes); omp's `cancel`, an `extension_ui_response` for that id written by `AgentBridge::send`, and this call each remove it; at most 64 per process (the oldest goes), gone with the process. Under the `sessions` lock it takes that prompt together with the same entry's stdin, so the answer can only reach the process incarnation that asked; no running process, no such prompt — one shown in the wrong tab, one from a process restarted under the same id, one already answered or granted, one evicted or never recorded — or a project grant for a process with no folder, and the call is rejected with nothing written and nothing saved. It then writes `{type: "extension_ui_response", id, value: "Approve"}` to that stdin, and only once that write succeeded grants the prompt's tool (under that process's own folder for project scope); a failed write puts the prompt back, saves no rule and is a rejection too. Answer-then-grant rather than grant-then-roll-back: a rollback could revoke a rule the user already had, and a rule saved first would auto-answer the process's other prompts while this one is still open. The session-scope insert runs under the bridge lock and only if the entry is still the incarnation the prompt came from, so it cannot outlive a reap that already cleared the session's grants. The command resolves to `null` (answered and granted) or a reason string (answered, rule not saved — the rules file failed, or the process was replaced right after the answer); a rejection always means omp got nothing. The buttons call `OMP_BRIDGE.approveAndRemember`, which settles the bubble at once (no second click can race the call) and then makes that one call for the prompt's own session, whichever tab is active by then. On a rejection it reopens the bubble (`_reopenAsk`) for a plain Approve/Deny and adds a note — never a fallback `send_command` Approve, which could answer a respawned process; on a reason string it adds an "approved, but the rule was not saved" note. Both only while the activation that settled the bubble is still shown. Revoke and list still act on the active tab: they only narrow or read.
