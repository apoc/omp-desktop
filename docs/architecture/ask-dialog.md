# Ask dialog

Once `set_ask_dialog {enabled: true}` is on, omp's ask tool reaches the desktop as one `extension_ui_request` with `method: "ask"` carrying every question of the call (`header`, options with `description`/`preview`, `multi`, `recommended`, an optional `timeout`). The flag is off by default and per process, so `_initFetch` sends it on every activation, like the subagent subscription; without it omp falls back to one `select` per question (plus an `editor` for typed text), which still works as plain prompts. `app/ask-dialog.js` (`window.OMP_ASK_DIALOG`, regression `test-ask-dialog.mjs`) holds the rules, `chat/ask-dialog.jsx` renders the card inside the ask bubble.

- The reply is `answers: [{id, selectedOptions, customInput?}]` (`OMP_BRIDGE.answerAskDialog`). omp validates it and fails the ask tool on any mismatch (rpc-mode.ts `parseAskDialogResponse`): one answer per question in request order, exact labels, and a pick-one question carries one option *or* typed text. `answers()` builds only that shape; the regression replays random clicks and typing against a port of omp's checks. A request the dialog cannot parse is cancelled, so omp never waits on it.
- The request reaches stdout *before* its ask tool's `tool_execution_start` (seen live), like a tool-approval `select`, so it goes through `_queueAskBubble` too; pushed on arrival it sits above its own tool card.
- A lone pick-one question with options answers on click; anything else sends on Submit, which waits until every pick-one question has an option or typed text (pick-any may stay empty). A lone pick-one question answered with nothing would read as a cancel in omp.
- Cancel sends `cancelled: true`, which makes omp abort the turn — as Esc does on omp's own dialog; Esc here keeps its window meaning (stop the turn). omp's `cancel` frame (turn stopped, or its `ask.timeout` ran out and it picked the recommended options itself) marks the bubble `closedByOmp`.
- Over RPC an answer has no note, no images and no "chat about this": the reply carries only `selectedOptions` and `customInput`.
- Picks not sent yet live in `ask-dialog.jsx`'s module map keyed by request id: the chat view remounts on a tab switch. Shift+Tab is stopped at the dialog so it moves focus instead of cycling the thinking level.
- `select` stays for tool approvals and extension pickers (`/review`), without a free-text box: those callers expect one of their own options.
- Tool approvals are that `select` with options exactly `["Approve","Deny"]` and a title `Allow tool: <name>` plus detail lines (omp `formatApprovalPrompt`: optional `Origin:`/`Reason:`, then the tool's `formatApprovalDetails()` — command, path, content preview). `app/approval.js` (`OMP_APPROVAL.approvalInfo`, regression `test-approval.mjs`) splits head from details and mirrors Rust's `approval::approval_tool_name` grammar, which decides whether the "allow for this session / project" buttons appear. A prompt an approval rule covers never reaches the frontend: `reader.rs` `try_auto_approve` answers it on omp's stdin and forwards `{type: "desktop_auto_approval", tool, details}` (`details` = the title after its first line, or `null`). `live.js` turns that into a desktop-made `kind: "approval"` row (`autoApprovalRow`, no `ts`) queued through `_queueAskBubble`, so it lands after its tool card like a manual prompt; `chat/approval-row.jsx` shows the tool and the first detail line that is not `Origin:`/`Reason:`, with the full details (plain text, never markdown) unfolding on click (#42). The frame carries no `toolCallId`, so the row is never merged into a card: with parallel calls a name match would be a guess.
- A standing grant ("allow for this session / project") is bound to the prompt, not to the active tab, and is made together with the prompt's "Approve" answer in one IPC call. The bubble carries its `sessionId` (the tab whose frames built it: `_switchToSession`'s listeners, and every step after an await, stop once their activation is superseded or detached) and its request `id`, and `approval_approve_and_grant` takes only those two plus the scope. Rust (`AgentBridge::approve_and_grant`, `agent/approvals.rs`) looks the prompt up among the ones that session's live process forwarded and that are still unanswered — the stdout reader records every approval prompt it did not auto-answer (ids up to 256 bytes); omp's `cancel`, an `extension_ui_response` for that id written by `AgentBridge::send`, and this call each remove it; at most 64 per process (the oldest goes), gone with the process. Under the `sessions` lock it takes that prompt together with the same entry's stdin, so the answer can only reach the process incarnation that asked; no running process, no such prompt — one shown in the wrong tab, one from a process restarted under the same id, one already answered or granted, one evicted or never recorded — or a project grant for a process with no folder, and the call is rejected with nothing written and nothing saved. It then writes `{type: "extension_ui_response", id, value: "Approve"}` to that stdin, and only once that write succeeded grants the prompt's tool (under that process's own folder for project scope); a failed write puts the prompt back, saves no rule and is a rejection too. Answer-then-grant rather than grant-then-roll-back: a rollback could revoke a rule the user already had, and a rule saved first would auto-answer the process's other prompts while this one is still open. The session-scope insert runs under the bridge lock and only if the entry is still the incarnation the prompt came from, so it cannot outlive a reap that already cleared the session's grants. The command resolves to `null` (answered and granted) or a reason string (answered, rule not saved — the rules file failed, or the process was replaced right after the answer); a rejection always means omp got nothing. The buttons call `OMP_BRIDGE.approveAndRemember`, which settles the bubble at once (no second click can race the call) and then makes that one call for the prompt's own session, whichever tab is active by then. On a rejection it reopens the bubble (`_reopenAsk`) for a plain Approve/Deny and adds a note — never a fallback `send_command` Approve, which could answer a respawned process; on a reason string it adds an "approved, but the rule was not saved" note. Both only while the activation that settled the bubble is still shown. Revoke and list still act on the active tab: they only narrow or read.

## Questions across app restarts

Unanswered **ask-tool questions** reappear when a saved conversation is resumed or reopened on launch. The restored card preserves the questions, choices, descriptions, previews, multi-select rules and recommended options. Parallel unanswered asks form one dialog so submitting one answer cannot strand the rest. Unsaved partial picks are still memory-only.

The bridge reads native `get_entries` after protocol negotiation. `get_messages` is provider-filtered and can omit the unfinished assistant tool call entirely, so it cannot be the recovery source. `OMP_ASK_RECOVERY.fromEntries` walks backward from the returned `leafId`; missing parents, cycles, duplicate ids and malformed questions fail closed. Only the current unanswered batch qualifies. Answered asks, explicit cancellations/aborts, a later user reply or completed assistant turn, and abandoned branches do not reopen. Native process-exit diagnostic results are not user answers. State/history reply order is immaterial; tab switches, conversation changes and new user/live-question events invalidate stale recovery requests.

Recovery never replays tools, invokes a model, reissues an approval or sends the dead process's request id. The card is labelled **restored**. Submitting validates the answer and sends the question/answer pairs as a normal user `prompt` to that conversation's current process, which continues from the reply. Slashes and angle brackets in the JSON data are escaped so quoted skill tokens and harness tags cannot dispatch commands. Live questions still use their original `extension_ui_response` callback. A rejected send leaves the restored card open with its error; in-flight controls cannot double-submit.

**Cancel** does not wake the agent. It stores the dismissed tool-call ids in local app storage under `omp-desktop:ask-dismissed:<conversation file>`, scoped by the full conversation path (and therefore its profile), so another launch does not restore a deliberately dismissed question. A failed storage write leaves it open with an error. Tool approvals and extension/OAuth pickers are not reconstructed: their dead execution context must never be treated as an active grant or callback.

`test-ask-recovery.mjs` exercises the public bridge against native-shaped filtered messages and raw entries, including branch isolation, grouped asks, cancellation persistence, refusal, live callbacks, command-token inertness and response ordering. The native smoke uses an isolated real omp process with a loopback-only model endpoint: the restored answer is persisted and remains settled after another process restart. The actual AskBubble/AskDialog controls are also exercised in Chromium against that native RPC process.
