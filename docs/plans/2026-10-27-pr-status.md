# Pull-request status across Changes and project navigation

Status: implementation approved on 2026-10-27. Execution and verification are tracked in the task list; installation and publishing are separate requests.

## Goal

Keep a branch's PR visible after merge and remote-head deletion. Show consistent lifecycle, draft, CI and unresolved-review indicators on the Changes card, left project sidebar, top project tabs and grouped conversation rows. Status discovery remains read-only and independent of Auto-fix permission.

## Evidence and current failure

- Native discovery requires the upstream GitHub ref before selecting a PR, and searches repository/parent PR lists for OPEN only. A missing ref therefore fails before completed PRs can be recognized.
- Completed PRs currently become a null snapshot, and feedback parsing only accepts OPEN. The wire snapshot has no lifecycle or overall CI state.
- The Changes icon is green for non-drafts, gray for drafts; it does not reflect merge or failed CI.
- The monitor retains a previous snapshot on read errors. That accounts for a green PR icon alongside a deleted-branch error.
- Only the active tab receives discovery results. Neither the sidebar nor project tabs receive PR status.
- The existing `threads` collection already excludes resolved and outdated review threads and retains one latest-comment identity per thread.
- Read-only GitHub query on 2026-10-27 confirmed upstream PR #61 is MERGED with a null remote ref; its former branch name, exact head oid, head repository and commit-associated PR remain queryable. Missing branch is not evidence that the PR is missing.

## User-visible contract

| Condition | Presentation |
| --- | --- |
| Open, ready for review | Green open-PR glyph; explicit CI indication where available |
| Draft | Gray, visually distinct draft-PR glyph, not only a different color |
| Open or draft with failed CI | Red PR indicator retaining its open/draft glyph; failed-CI marker/count and accessible description |
| Checks running or queued | Amber pending-CI indicator; never described as passed |
| No checks / unknown check result | Neutral CI indication; never described as passed |
| Merged | Purple merge glyph and “Merged”, even when the head branch has been deleted |
| Closed without merge | Red closed-PR glyph and “Closed” |
| Outstanding review feedback | Comment bubble with number of unresolved, non-outdated review threads |
| Fetch failure after a known result | Keep the cached lifecycle/CI/review display unchanged, quietly skip the attempt, and block automation until a fresh valid read; retry on the existing cadence |
| No matching PR | Ordinary no-PR state, without borrowing another branch's historical PR |

Lifecycle takes precedence over historical CI: a merged PR remains purple even if an old check failed. CI failure takes precedence over the normal open/draft color, but not the draft shape. Pending CI and review-count badges are independent signals. Terminal PRs do not show an actionable-review badge or offer Auto-fix.

“3 comments to address” means three unresolved review threads, not three replies, total discussion comments, resolved threads, or outdated threads. Tooltips/accessibility labels make that meaning explicit. Zero hides the bubble. This reuses the current actionable-feedback definition rather than adding a second review policy.

## Scope and non-goals

- Use the existing GitHub CLI authentication, supervised requests, bounded output and GraphQL connection limits.
- Keep the current actual-worktree folder binding; never query the source-project folder in place of a conversation's checkout.
- No new GitHub webhook, service, dependency, push notification, PR mutation, merge/reopen action, or automatic branch cleanup.
- Do not infer completion from a missing ref, transcript text, a branch-name match alone, or ancestry on main.
- Keep existing approval, goal/plan, readiness and same-folder busy-tab guards. An open draft remains eligible for explicitly enabled Auto-fix, as before.
- Respect Settings → Rail → Changes: off hides these PR indicators, stops status reads and revokes Auto-fix, preserving the existing feature gate.
- Leave the already-applied title-bar work unchanged.
- The user approved implementation. Reinstalling and publishing remain separate requests; this execution does not replace the installed application.

## Slice 1 — Native lifecycle discovery and snapshot contract

Target: `src-tauri/src/pr_automation/{mod,feedback,git,tests}.rs`.

1. Add validated lifecycle `state: OPEN | MERGED | CLOSED` to the snapshot. Keep `isDraft` separate from lifecycle.
2. Add normalized `checksState: none | pending | success | failure | unknown`, derived from GitHub's latest-commit check rollup; retain `failedChecks` for remediation and counts. No rollup means no checks, not success. Reject unsupported/malformed API values instead of treating them as success.
3. Query candidate PRs across lifecycle states in the head repository and its parent. Query commit associations by local HEAD oid independently of whether the remote branch ref still exists. Keep every connection bounded and reject truncated discovery.
4. Match head repository, configured upstream branch and exact PR head oid. Prefer a unique current open PR; preserve synchronization errors for an open branch whose remote head differs. Never resurrect an older merged PR over a reused branch with an open PR or a different current remote head.
5. If no current open candidate exists, accept a unique MERGED/CLOSED candidate matching that exact identity, including when its remote ref is null. A genuinely missing branch without a proven terminal match remains an explicit error. Ambiguous candidates stay errors, not an arbitrary newest-PR guess.
6. Parse completed snapshots without requiring a live head ref. Validate local branch/HEAD/upstream before and after the network read. Preserve fork/head-repository checks and fail closed for unsupported fork targets.
7. Accept an OPEN → MERGED/CLOSED transition between discovery and the detail query if identity still matches; terminal status is not a detection error. A reopen or identity/head change requires fresh open-PR validation before it can become actionable.

Acceptance: a fresh read of a checkout for a merged PR whose branch has been deleted returns the merged snapshot, not null or an upstream-ref error. Existing ambiguity, authentication, synchronization and response-limit safeguards remain effective.

## Slice 2 — Shared read-only status and Auto-fix safety

Target: `src/app/{pr-automation.js,use-pr-automation.jsx}`, `src/live.js`, `src/app-live.jsx` and their existing regression scripts.

1. Extend snapshot validation and migrate every fixture/consumer to the lifecycle and CI contract. No compatibility alias or implicit OPEN default.
2. Expose read-only status for all open conversation checkouts, not just the selected tab. Adapt the existing monitor rather than create a separate polling mechanism per component.
3. Deduplicate reads for tabs sharing the same canonical actual folder and branch. Keep per-tab Auto-fix grants separate; sharing status never shares permission. Different worktrees/branches remain different discovery targets even when grouped under one source project.
4. Use a single coalescing request queue, prioritizing the active checkout. Refresh on tab/branch changes, turn completion, app focus/visibility and on a shared 30-second cadence while the app is visible. Stop inactive display polling while hidden, and stop all reads when Changes is disabled. Preserve existing selected-tab Auto-fix scheduling/gates.
5. Permit background read-only bridge requests guarded by registered tab id, actual folder, branch and process/conversation incarnation. Remove only the active-tab requirement from reads, not from sends. Drop stale results after tab close, branch/folder/profile changes or process replacement. Do not activate background tabs to read their status.
6. Clear obsolete statuses and counts immediately on identity changes; prune closed tabs and deduplicated targets with no remaining owners. Per the subsequent user-approved failure policy, a missed fetch retains the display unchanged without warning flicker, but invalidates its use for automation. Startup failure remains unknown; successful no-PR/terminal results still clear/revoke appropriately. Malformed-data warnings remain explicit.
7. On MERGED/CLOSED, revoke Auto-fix and keep the terminal snapshot visible. Reject enabling Auto-fix on a known terminal PR. Check `state === OPEN` in both the controller and the bridge's fresh snapshot immediately before prompt handoff, even when PR URL/branch/head have not changed.
8. Reopening does not restore an old grant. A prompt already handed to the agent cannot be recalled; do not terminate unrelated running work to implement terminal-state handling.

Acceptance: inactive project rows obtain status without starting agents or enabling automation. A merge between discovery and dispatch produces no fix prompt. Stale reads never overwrite another branch's indicators.

## Slice 3 — One status presentation on every requested surface

Target: Changes card; shared PR status presentation helpers/component; project sidebar; top tab bar and grouped member dropdowns; relevant CSS and `src/index.html` load order.

1. Implement one pure status/precedence model and one reusable icon/badge component. Keep lifecycle, CI, comments and discovery freshness separate from automation status.
2. Render the same glyphs, colors and thread count in the Changes card, individual sidebar conversations and individual project tabs/dropdown members. Retain the agent run-state dot and worktree indicator; PR failure must not impersonate an agent-process failure.
3. Add a visible lifecycle label to the Changes card metadata and retain title, PR number/link and diff counts. Keep link/menu behavior; the review bubble opens the PR review discussion from the card. Do not create nested buttons in clickable navigation rows; navigation remains navigation, with a descriptive tooltip.
4. For a collapsed multi-conversation project, aggregate distinct PRs, deduplicating by repository/PR identity and thread id. Surface failed open CI first, then unresolved-review attention. Show a multiple-PR cue/tooltip when members differ rather than claiming the entire project is merged or draft. Expanded members keep their exact branch-specific status. Multiple tabs on the same PR must not multiply its counts.
5. Use purple for merged and a genuinely distinct draft/closed/merge glyph, plus labels/tooltips so meaning is not color-only. Expose descriptions such as “Draft pull request #42; 1 failed check; 3 unresolved review threads”.
6. Preserve project names, worktree/profile labels, keyboard navigation, reorder targets and close buttons. Truncate names before hiding compact status badges; verify narrow layouts and long titles.

Acceptance: one PR displays the same status/count across card and navigation; grouped worktrees never bleed status into one another or double-count a shared PR.
